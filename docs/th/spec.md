# VAL — ตัวภาษา

> **ฉบับแปล** ตัวบทที่ใช้ตัดสินคือ [ฉบับภาษาอังกฤษ](../spec.md) ที่ใดที่คำแปล
> เคลื่อนจากต้นฉบับ ให้ถือตามต้นฉบับ

**สถานะ:** ร่าง 2026-08-17 ยังไม่มีอะไรในนี้ถูกสร้างขึ้น นี่คือข้อกำหนดไว้ให้
เถียงด้วย คำถามที่ยังเปิดอยู่ใน §11 เปิดอยู่จริง และข้อเสนอแนะใต้แต่ละข้อคือสิ่งที่
เอกสารส่วนที่เหลือสมมติไว้จนกว่าจะมีใครบอกเป็นอย่างอื่น

VAL เป็น **ภาษาเฉพาะโดเมน ไม่ใช่ภาษาใช้ทั่วไป** และเป็นภาษา **total**:
ทุกโปรแกรมหยุด และคอมไพเลอร์รู้ (§6) หลักการออกแบบคือเปลือกเชิงประกาศกับชั้น
นิพจน์เล็กๆ — โครงสร้างชั้นนอกเป็นข้อมูล ส่วนนิพจน์ชั้นในคุ้นตาสำหรับใครก็ตามที่
เคยเขียน TypeScript หรือ Dart

ครึ่งหลังนั้นเป็นข้อจำกัด ไม่ใช่อารมณ์ เปลือกจะคิดอะไรขึ้นมาใหม่ก็ได้เท่าที่จำเป็น
เพราะไม่มีอะไรอื่นหน้าตาเหมือนมัน ชั้นนิพจน์ทำแบบนั้นไม่ได้: มันยืม `const`
`function` `switch` `?:` spread `T?` และ `List<T>` มาจากภาษาที่ผู้อ่านมีอยู่แล้ว
และในที่ที่ต้องคิดโครงสร้างใหม่ขึ้นมา คำตอบมักคือเปลือกควรจะจัดการเรื่องนั้นเอง
DSL ที่นิพจน์ของมันเป็นสำเนียงที่สี่ ทำให้ผู้อ่านจ่ายสองเท่า

### ผู้อ่านสองกลุ่ม

โปรแกรม VAL มีผู้อ่านสองกลุ่ม และไม่ใช่คนกลุ่มเดียวกัน

**เปลือกถูกอ่านโดยคนที่ไม่ได้เขียนโค้ด** พาร์ตเนอร์ที่กำลังตัดสินใจว่าจะเผยแพร่แอป
ไหม เจ้าหน้าที่กำกับที่ถามว่ามันแตะอะไรบ้าง ผู้ตรวจความปลอดภัย และเจ้าของ
credential ที่มันอยากได้ พวกเขาอ่าน `capabilities` `trust` `require` `verify`
และ `execute` และต้องตอบคำถาม "สิ่งนี้ทำอะไรกับฉันได้บ้าง" ได้โดยไม่ต้องเรียน
ภาษาก่อน

**ชั้นนิพจน์ถูกเขียนโดยคนที่เขียนโค้ด** เลขคณิต การจัดการ string การหาระดับชั้น
มันควรน่าเบื่อและคุ้นเคย ซึ่งเป็นสิ่งที่การยืมจาก TypeScript และ Dart ซื้อมาให้

**ที่ใดที่สองอย่างขัดกัน ให้ย้ายงานไปไว้ในเปลือก** นั่นคือกฎ และมันเปลี่ยนไปแล้ว
สามอย่าง: `update` เป็นตารางของฟิลด์แทนที่จะเป็น spread ซ้อนกัน `require` ใช้
`exists` แทน `!= null` และการค้นหาที่จะกลายเป็นโซ่ `?:` กลายเป็น `switch`
ที่อ่านเหมือนตาราง แต่ละอย่างย้ายการตัดสินใจออกจากครึ่งที่คนนอกอ่านไม่ได้

ราคาคือเปลือกที่ใหญ่ขึ้น — คีย์เวิร์ดมากขึ้น บล็อกมากขึ้น ไวยากรณ์มากขึ้น
นั่นเป็นที่ที่ควรจ่าย เพราะเปลือกคือส่วนที่ถูกอ่านบ่อยกว่าถูกเขียนเป็นร้อยเท่า

## 1. VAL มีไว้ทำอะไร

แอปที่เขียนด้วย VAL ประกาศว่ามันทำอะไรได้ก่อนที่มันจะทำ และสิ่งที่มันทำไปจริงๆ
ถูกตรวจย้อนหลังได้โดยคนที่ไม่ได้อยู่ตรงนั้น

นั่นคือทั้งหมด คุณสมบัติที่มักถูกไล่รายการ — โครงสร้างเชิงประกาศ ความไม่เปลี่ยนแปลง
ความเป็น deterministic ความปลอดภัยแบบ capability effect ที่ประกาศชัด — ไม่ใช่
รายการฟีเจอร์ แต่ละอย่างอยู่ที่นั่นเพราะถ้าตัดออก ประโยคข้างบนจะพัง

**sandbox กับสิ่งนี้ไม่ใช่อย่างเดียวกัน** sandbox ยืนยันว่าแอป*ทำบางอย่างไม่ได้*
มันไม่ได้บอกอะไรเลยว่าแอป*ทำอะไรลงไป* เมื่อแอปลงมือแทนใครสักคนแล้ว — ยื่น
credential ย้ายเงิน เซ็นข้อมูล — คำถามที่สองคือคำถามที่กำลังถูกถาม และการแยกกัน
อยู่ไม่ได้ตอบมัน

### Host

VAL ไม่มี I/O มันไม่รู้จักว่าที่เก็บ credential ระบบชำระเงิน เครือข่าย หรือหน้าจอ
คืออะไร มันคำนวณ และในที่ที่ต้องมี effect มันปล่อยคำอธิบายของ effect ออกมา:

```
EffectRequest { capability, operation, payload }
```

**host** เปลี่ยนสิ่งเหล่านั้นให้เป็นจริง หรือปฏิเสธมัน มันตัดสินตามลำดับ:
capability ถูกประกาศไว้ไหม · ผู้ใช้ยินยอมหรือยัง · policy ของ host อนุญาตไหม ·
แอปน่าเชื่อถือไหม · ปฏิบัติการนี้อยู่ในขอบเขตไหม แล้วจึงค่อยมีอะไรเกิดขึ้น

[Vaulet](https://vaulet.id) เป็น host แรกและเป็นเหตุผลที่ VAL มีอยู่ มันไม่ได้มี
อภิสิทธิ์ในตัวภาษา ที่ใดที่ภาษาต้องการสิ่งที่มีแต่ host จัดหาได้ — การเข้ารหัส
แบบ canonical นาฬิกา ความสุ่ม การไล่ห่วงโซ่ความเชื่อถือ — อินเทอร์เฟซถูกระบุไว้
ที่นี่และ host เป็นผู้ทำให้เกิดขึ้น

### พูดเทียบกับสิ่งที่มันคล้าย

บล็อกเชนตอบสามคำถาม: การรันหมายถึงอะไร ใครตัดสินว่ามันเกิดขึ้นแล้ว และ state
อยู่ที่ไหน สิ่งนี้ก็ตอบเหมือนกัน แต่ตอบต่างออกไป

```
บล็อกเชน = เครื่องสถานะที่ตรวจสอบได้ + ฉันทามติแบบกระจาย
                                    + state ส่วนกลางที่ถูกทำสำเนา

VAL     = เครื่องสถานะที่ตรวจสอบได้ + ความปลอดภัยแบบ capability
                                    + state ส่วนตัวที่อยู่กับเครื่อง
                                    + หลักฐานที่ส่งต่อได้
                                    + อำนาจที่มีอยู่แล้ว
```

พจน์แรกเหมือนกัน และนั่นคือเหตุผลที่สิ่งนี้มีกลิ่นของภาษาสัญญา: ความเป็น
deterministic และ totality คือสิ่งที่การรันซ้ำอย่างอิสระต้องการ ความต่างอยู่ที่ว่า
ใครรันซ้ำ บล็อกเชนถูกรันซ้ำโดยทุกคน ส่วน action ของ VAL ถูกรันซ้ำโดยคนที่คุณ
ยื่นหลักฐานให้

**หลักฐานมาแทนการทำสำเนา ไม่ใช่แทนฉันทามติ** บล็อกเชนคัดลอก state เพื่อให้ใครก็
ตรวจได้ สิ่งนี้เก็บ state ไว้แล้วแจก proof ออกไป เป้าหมายเดียวกัน ทิศทางการเดินทาง
ตรงข้ามกัน

**ความปลอดภัยแบบ capability ไม่ได้มาแทนฉันทามติ** และการทำเป็นว่าใช่คือการซ่อน
ช่องว่างที่มีจริง ทั้งสองอยู่คนละแกน: ฉันทามติตัดสินย้อนหลังว่าเรื่องเล่าฉบับของใคร
นับ ส่วน capability ตัดสินล่วงหน้าว่าอะไรพยายามทำได้บ้าง สิ่งที่ฉันทามติให้และ
สิ่งนี้ไม่ให้ คือการป้องกันคนที่เขียนประวัติของตัวเองใหม่ — สิ่งที่มายืนแทนคือ
ความทรงจำของผู้ตรวจสอบเรื่องรากล่าสุดที่มันเห็น และลายเซ็นของผู้ออกครอบรากที่
credential อนุมานมา (§7) นั่นอ่อนกว่า โดยตั้งใจ

**พจน์สุดท้ายคือพจน์ที่พลาดง่ายที่สุด** การขุดและการวางเดิมพันมีอยู่เพื่อผลิตอำนาจ
ขึ้นในที่ที่ไม่มีอำนาจอยู่ — โลกที่ไม่มีใครมีสิทธิ์บอกว่าอะไรจริง VAL ไม่เคยผลิต
อำนาจขึ้นมา เพราะผู้มีอำนาจอยู่ตรงนั้นอยู่แล้ว: CSCA ของรัฐ โบรกเกอร์ที่มี
ใบอนุญาต นายจ้าง ธนาคาร

> บล็อกเชนผลิตอำนาจขึ้นในที่ที่ไม่มี VAL ส่งผ่านอำนาจที่มีอยู่แล้ว

ซึ่งลากเส้นขอบของการออกแบบนี้อย่างซื่อสัตย์: ไม่มีอะไรที่นี่ให้ฉันทามติ ดังนั้น
**การส่งต่อมูลค่าแบบผู้ถือระหว่างคนแปลกหน้าอยู่นอกขอบเขต** ตราบใดที่แต้มใช้ได้
เฉพาะกับผู้ที่ออกมันให้ ก็มีคู่กรณีรายเดียวที่มีสิทธิ์ระงับข้อพิพาทเรื่องแต้มนั้น
และไม่ต้องมีบัญชีแยกประเภท วันที่แต้มโอนกันได้และร้านค้าที่ไม่เชื่อผู้ออกยอมรับมัน
ย่อหน้านี้จะเลิกเป็นจริง และคำถามนี้ต้องถูกถามใหม่

### ใครถูกเชื่อ

**แอปไม่ถูกเชื่อ** ผู้เผยแพร่ของมันเขียนโค้ดที่เราไม่ได้ตรวจทีละบรรทัด อาจเป็น
บริษัทที่ไม่มีใครเคยได้ยิน และมีผลประโยชน์ใน credential ของผู้ใช้ที่ไม่ใช่
ผลประโยชน์ของผู้ใช้ ไม่มีอะไรในเอกสารนี้สมมติเป็นอย่างอื่น และทุกกฎที่ดูเหมือน
ความไม่สะดวกคือข้อสมมตินั้นถูกนำมาใช้

**host ถูกเชื่อ** โดยผู้ใช้ เพราะเขาเลือกมันเองและเพราะมันถือกุญแจของเขา
มันคือสิ่งที่จำกัดขอบเขต capability วาดใบยินยอม ทำการเปิดเผย ถือโทเคน และปฏิเสธ

ผลสองข้อที่พลาดง่ายและแพงถ้ารู้ช้า:

**package ต้องตรวจสอบตัวเองได้จากตัวมันเอง** ทุกการตรวจในเอกสารนี้ — ตำแหน่งของ
effect การประกาศ capability ที่มาของข้อมูล totality ความครบถ้วนของกิ่ง ความครบ
ของ text bundle ขอบเขตที่ทำให้วงจรมีขนาดจำกัด — ถูกรันใหม่*โดย host* บน package
ที่มันได้รับ การที่ build ของผู้เผยแพร่ผ่านไม่พิสูจน์อะไรเลย: build เป็นของเขา
ดังนั้นจึงต้องไม่มีอะไรที่ตรวจได้เฉพาะด้วยข้อมูลนอก package และตัวตรวจต้องเล็กพอ
ที่จะรันบนมือถือตอนติดตั้ง นั่นเป็นอีกเหตุผลที่ภาษานี้เล็กและ total และเป็น
ข้อจำกัดของทุกอย่างที่จะถูกเพิ่มเข้ามาทีหลัง

**ตัวสิ่งที่ส่งมอบคือ source** v1 ส่งโปรแกรมเป็น VAL และเดิน AST ที่มี type
สิ่งที่ผู้ตรวจอ่านจึงเป็นสิ่งที่รัน — ไม่มีก้อนที่คอมไพล์แล้วให้ต้องเทียบกับ
repository ที่ไม่มีใครเห็น เมื่อ Wasm back end มาถึง (§8) เรื่องนี้จะเลิกฟรี:
package ต้องยังพา source ไปด้วยและให้ host คอมไพล์เอง หรือไม่ build ก็ต้อง
ทำซ้ำได้ การส่งแต่ bytecode จะพาผู้เผยแพร่กลับไปสู่ตำแหน่งที่ถูกเชื่อ ซึ่งหัวข้อนี้
เพิ่งเอาออกไป

## 2. รูปร่างของโปรแกรม

```
app "th.co.codefin.loyalty"
version 1

capabilities { … }        // ทุกอย่างที่แอปนี้จะขอได้ตลอดอายุของมัน
enum · credential · type  // การประกาศ
state { … }               // สิ่งที่คงอยู่ระหว่าง action
trust … { … }             // policy การตรวจสอบที่มีชื่อ
function … { … }          // helper แบบ pure
action … { … }            // สิ่งเดียวที่รันได้
```

**แอปหนึ่งตัวคือ package หนึ่งชุด และ package หนึ่งชุดมีได้หลายไฟล์** พวกมันใช้
scope ร่วมกัน: ไม่มี namespace ต่อไฟล์และไม่มีคำสั่ง import เพราะไฟล์คือวิธีที่
ผู้เขียนจัดระเบียบงานของตัวเอง ไม่ใช่เส้นแบ่งที่คนอื่นต้องมาไล่ตาม ผู้ตรวจยังหาเจอ
ทุกอย่างด้วยการค้นครั้งเดียว

**ไม่มีการ import ข้าม package** สิ่งเดียวที่ควรค่าแก่การแบ่งปันคือ helper แบบ
pure กับ trust policy — helper ที่ใช้ร่วมกันจริงๆ ควรอยู่ในชุดปิดของ builtin
ส่วน policy ที่ใช้ร่วมกันถูกเผยแพร่ในทะเบียนและถูกอ้างด้วยแฮชของมัน แบบเดียวกับ
คลังคำของ claim (ADR 0046) สิ่งที่ไม่มีให้คือ dependency ที่คนอื่นเปลี่ยนได้
หลังจากคุณเซ็นไปแล้ว

ตัวระบุแอปเป็น **string ในเครื่องหมายคำพูด** ไม่ใช่ชื่อที่มีจุดแบบเปลือย:
ตัวระบุแบบ reverse-DNS กับการเข้าถึงฟิลด์มีรูปร่างเดียวกัน และ lexer ไม่ควรต้อง
แยกทั้งสองด้วยบริบท

### กฎไวยากรณ์ที่ทุกอย่างอื่นสมมติไว้

**การขึ้นบรรทัดใหม่จบคำสั่ง และไม่มีอัฒภาค** — ยกเว้นภายในวงเล็บที่ยังไม่ปิด
ซึ่งคำสั่งจะเดินต่อ นิพจน์ยาวๆ ถูกห่อด้วย `( … )` โดยตั้งใจ ซึ่งทำให้ความซับซ้อน
มองเห็นได้แทนที่จะซ่อนอยู่ กฎที่ว่าบรรทัดซึ่งจบด้วยตัวดำเนินการจะเดินต่อนั้น
จงใจไม่รับมาใช้: ภาษาที่ขายเรื่องการไม่มีเซอร์ไพรส์ไม่ควรนำเข้ากฎข้อเดียวที่
ทั้งอุตสาหกรรมเดาผิดมายี่สิบปี

**ตัวคั่นเดินตามผู้อ่านสองกลุ่ม** เปลือกคั่นด้วยการขึ้นบรรทัดใหม่ ส่วนภายในนิพจน์
สมาชิกคั่นด้วยจุลภาค `member.tier: tier` อยู่บนบรรทัดของมันเอง ส่วน
`{ ...member, tier: tier }` ใช้จุลภาค กฎเดียว และเป็นกฎเดียวกับที่ตัดสินทุกอย่าง
เรื่องใครอ่านอะไร

**คีย์เวิร์ดถูกจอง ไม่ใช่ขึ้นกับบริบท** การตรวจนี้ไม่ใช่ทฤษฎี: จาก 57 claim
ในคลังคำที่จองไว้วันนี้ ไม่มีอันไหนชนกับคีย์เวิร์ด — และคลังคำเลี่ยง `state`
ด้วยการเขียนเป็น `address.region` อย่างที่ OpenID Connect ทำ คีย์เวิร์ดตามบริบท
มีราคาเป็นข้อความ error ที่แย่ลงในทุกความผิดพลาด และมันถูกซื้อมาที่นี่เพื่อรับมือ
การชนที่ไม่มีอยู่จริง

**จุดคือการเข้าถึงฟิลด์เสมอ** ชื่อ claim ในทะเบียนเขียนเป็น path —
`address.postal_code` `address.region` — เพราะ credential แยกสิ่งเหล่านั้นออกจากกัน
(ADR 0031) และนั่นคือโครงสร้าง ไม่ใช่ชื่อที่มีจุดอยู่ข้างใน type ของ credential
เปลี่ยนมันเป็นโครงสร้าง และ VAL อ่านมันเป็นโครงสร้าง ผลที่ตามมาต้องพูดออกมา
แทนที่จะปล่อยให้ไปค้นพบเอง: **`claims.address` เดี่ยวๆ ไม่ใช่ค่า** เพราะไม่มี
ผู้ออกรายไหนเคยเซ็น claim ชื่อนั้น และคอมไพเลอร์บอกอย่างนั้นแทนที่จะยื่น record
ที่ครึ่งหนึ่งของฟิลด์ว่างเปล่ากลับมา

**`if` และ `switch` ใส่วงเล็บให้เงื่อนไข** อย่างที่ TypeScript และ Dart ทำ และ
อย่างที่ Rust ไม่ทำ เหตุผลไม่ใช่รสนิยม: มันกำจัดความกำกวมทุกจุดระหว่างบล็อกกับ
record literal ซึ่งเป็นกรณีพิเศษที่ Rust ต้องเพิ่มกฎขึ้นมารองรับ

**ตัวเลข** เป็นฐานสิบ ใส่ `_` ระหว่างหลักได้ — `100_000` ไม่ใช่ `_1` หรือ `1_`
ไม่มีฐานสิบหก ไม่มีฐานสอง ไม่มีเลขยกกำลัง: โครงการสะสมแต้มไม่ได้ใช้มัน และแต่ละ
อย่างเป็นวิธีเขียนตัวเลขที่ผู้ตรวจอ่านไม่ออกในพริบตา

`12.50` **ถูก lex เป็นโทเคนเดียวแล้ว parser ปฏิเสธมัน** แทนที่จะให้ lexer แยกมัน
เป็น `12` `.` `50` แล้วรายงานว่า "คาดว่าจะเจอชื่อฟิลด์" ทั้งไฟล์ `rejected.val`
ตั้งอยู่บนเรื่องนี้: กฎถูกสอนด้วยข้อความที่มันผลิตออกมาเท่านั้น

**ตัวระบุเป็น ASCII** string เป็น UTF-8 เต็มรูปแบบและข้อความภาษาไทยอยู่ในนั้น
แต่ภาษาที่ตัดสินว่าใครเป็นใครจะมีตัวระบุที่ `а` ซีริลลิกกับ `a` ละตินเป็นคนละชื่อ
แต่หน้าตาเหมือนกันเป๊ะไม่ได้ ความอ่านง่ายที่เสียไปถูกกู้คืนในที่ที่มันควรอยู่:
สิ่งที่ผู้ใช้อ่านคือใบยินยอมและคำอธิบายของแอปเอง ซึ่งมาจาก manifest ที่ถูกเซ็น
ไม่ใช่จากตัวระบุที่ใครจะตั้งอย่างไรก็ได้

**ชื่อที่โปรแกรมนี้ตั้งเองเป็น camelCase** — `lifetimePoints` `tierFor`
**ส่วนชื่อ claim ที่มันไม่ได้ตั้งถูกปล่อยไว้อย่างนั้น**: `purchased_at`
`document_number` และที่เหลือมาจากคลังคำของผู้ออก และการเขียนใหม่ให้ดูเหมือนโค้ด
ท้องถิ่นจะซ่อนข้อเท็จจริงเดียวที่สำคัญเกี่ยวกับมัน คือคนอื่นเป็นคนนิยามมัน

**อาร์กิวเมนต์ถูกระบุชื่อเมื่อมีตั้งแต่สองตัวขึ้นไป**

```
payment.request(to: merchant, amount: 12000)     // อ่านได้โดยไม่ต้องมีเอกสาร
payment.request(merchant, 12000)                 // ถูกปฏิเสธ
```

อาร์กิวเมนต์ตัวเดียวเป็นแบบตำแหน่งได้ — `tierFor(total)` — เพราะไม่มีอะไรให้สับสน
ด้วย เกินหนึ่งตัวขึ้นไป จุดที่เรียกถูกอ่านบ่อยกว่าถูกเขียนมาก และบ่อยครั้งอ่านโดย
คนที่กำลังตัดสินว่าจะอนุมัติสิ่งที่มันทำหรือไม่ ตัวเลขคู่หนึ่งที่ไม่มีป้ายกำกับคือ
จุดที่ผู้อ่านคนนั้นหยุดพอดี

## 3. ค่าและ type

`string int bool date datetime bytes` record type ที่นิยามเอง enum
`List<T>` `T?` `Verified<P>` `Proof<bool>`

**`int` เป็น 64 บิตมีเครื่องหมาย และเลขคณิต trap เมื่อล้น** การ trap เป็น
ทางเลือกเดียวที่ deterministic — การวนกลับให้คำตอบผิดที่ execution record จะไป
พิสูจน์มันอย่างซื่อสัตย์ ซึ่งแย่กว่าการล้มเหลว การ trap ยกเลิก action และไม่
commit อะไรเลย

**string ถูกเทียบและถูกส่งต่อ ไม่เคยถูกประกอบ** ไม่มี interpolation ไม่มี `+`
นี่ไม่ใช่เรื่องราคาของ lexer: ทุกประโยคที่ผู้ใช้อ่านต้องมาจากสิ่งที่ถูกเซ็นแล้ว
และ string ที่ประกอบตอนรันคือประโยคที่ไม่มีใครตรวจ — ซึ่งจะทำให้กฎห้ามเลียนแบบ
หน้าตาของ host บังคับใช้ไม่ได้ในวันที่ UI มาถึง ข้อความสำหรับคนอยู่ใน manifest
เป็นแม่แบบที่มีช่องซึ่งมีชื่อ และโค้ดเป็นคนใส่ค่า (§9) key แบบประกอบใช้
อาร์กิวเมนต์ที่มีโครงสร้าง ไม่ใช่การต่อ string:
`storage.write(scope: "member", id: memberId, …)`

**การหารด้วยศูนย์ trap** เหมือนการล้นและด้วยเหตุผลเดียวกัน: ตัวเลขผิดที่
execution record จะไปพิสูจน์อย่างซื่อสัตย์แย่กว่าการล้มเหลว แอปที่มีคำตอบที่มี
ความหมายสำหรับตัวหารเป็นศูนย์ก็เขียนมันออกมา

**ไม่มี floating point** สองเหตุผล และข้อเดียวก็พอ: รูปแบบบิตของ NaN เป็นแหล่ง
ความไม่แน่นอนหลักภายใต้ Wasm (§8) และเงินกับแต้มก็ต้องการจำนวนเต็มหรือทศนิยม
ตรึงตำแหน่งอยู่แล้ว จำนวนเงินเป็นหน่วยย่อย

ฟิลด์ใน `state` ประกาศค่าเริ่มต้นด้วย `default` ไม่ใช่ `=`:

```
state {
  member:         LoyaltyMember?
  lifetimePoints: int default 0
}
```

`=` ไม่ปรากฏที่ไหนเลยในภาษานี้ และข้อยกเว้นหนึ่งข้อในการประกาศ state ที่คงอยู่
ถาวรคือที่ที่แย่ที่สุดที่จะเก็บมันไว้

การผูกชื่อเฉพาะที่ใช้ `const` ไม่มี `var` และไม่มีการกำหนดค่า: ทุกการผูกเป็นที่
สิ้นสุด และ record ถูกอนุมานขึ้นใหม่แทนที่จะถูกเปลี่ยน

ใช้ `const` ไม่ใช่ `let` ทั้งที่ไม่มีอะไรที่นี่เปลี่ยนแปลงได้ และความต่างที่
`const` มักใช้ทำเครื่องหมายก็ไม่มีอยู่ คำนี้ถูกเลือกเพื่อผู้อ่าน: สำหรับคนที่มา
จาก TypeScript `let` ประกาศว่านี่คือตัวแปรที่จะถูกกำหนดค่าใหม่ ซึ่งตรงข้ามกับ
ทุกการผูกในภาษานี้

### ไลบรารีเป็นชุดปิด

มีชุด builtin ตายตัว — duration, list combinator ใน §6, การเทียบ string —
ที่ host เป็นผู้ทำให้เกิดขึ้น และ **แอปเพิ่มเข้าไปไม่ได้**

totality คือเหตุผลที่มันต้องปิดมากกว่าแค่เล็ก: builtin เป็นที่เดียวที่ปฏิบัติการ
ซึ่งไม่จบจะเล็ดลอดเข้ามาในภาษาที่พิสูจน์ไปแล้วว่ามีสิ่งนั้นไม่ได้ อีกเหตุผลคือ
DSL ที่มี prelude ต่อเติมได้คือภาษาใช้ทั่วไปที่ยังไม่ยอมรับตัวเอง

ถ้า helper ตัวหนึ่งใช้บ่อยพอที่สามแอปเขียนมันขึ้นมาเอง นั่นเป็นเหตุผลให้เพิ่มมัน
เข้าไปในชุด ไม่ใช่เหตุผลให้เปิดชุด

### Record ถูกอนุมานขึ้นใหม่ ไม่เคยถูกแก้

```
const bumped = { ...member, points: member.points + earned }
```

spread ผลิตค่าใหม่โดยแทนที่ฟิลด์ที่ระบุชื่อ มันมี type: ผลลัพธ์เป็น record type
เดียวกับค่าที่ถูก spread การ spread จึงคิดฟิลด์ขึ้นใหม่หรือทำฟิลด์หายไม่ได้

นี่คือวิธีอนุมาน record **ในนิพจน์** state ไม่ได้ถูกอนุมานแบบนี้: `update`
เป็นตาราง patch (§5) เพราะ spread ซ้อนกันคือรูปร่างของภาษานี้ที่คนที่ไม่ได้เขียน
โปรแกรมตามไม่ทันเป็นอย่างแรก

ไม่ว่าทางไหน ก็ไม่มี `a.b.c = v` ที่ไหนในภาษานี้ ในเฟสไหนก็ตาม

### Enum ถูก switch อย่างครบถ้วน

```
const discount = switch (tier) {
  Tier.bronze => 0,
  Tier.silver => 5,
  Tier.gold   => 10,
}
```

**`switch` เหนือ enum ใช้กิ่ง default ไม่ได้** การเพิ่ม `Tier.platinum` ต้อง
ทำให้ทุกโปรแกรมที่ตัดสินอะไรบางอย่างต่อระดับชั้นพัง — นั่นคือคุณค่าทั้งหมดของ
การมี enum แทนที่จะเป็น string ส่วน switch เหนือโดเมนเปิด (`int` `string`)
ต้องมี `default` เพราะมันครบถ้วนไม่ได้

### เงื่อนไข

`if` เป็นคำสั่ง รูปแบบที่เป็นนิพจน์คือตัวดำเนินการเงื่อนไข อย่างใน TypeScript
และ Dart:

```
const fee = amount > 100_000 ? 0 : 20
```

`if` ที่มีบล็อกเป็นตัวและให้ค่าออกมาเป็นรูปร่างของ Rust ไม่ใช่ของภาษานี้ และการ
ผสมทั้งสองให้วิธีเขียนสิ่งเดียวกันสองวิธี

## 4. การตรวจสอบ

### `verify` เป็นทางเดียวที่จะได้ `Verified<P>`

ไม่มี cast ไม่มี constructor ไม่มีการยืนยันตอนรันที่ปล่อยให้ type เหมือนเดิม
ฟังก์ชันที่เรียกร้องข้อมูลที่ตรวจแล้วจะถูกยื่นอย่างอื่นให้ไม่ได้ การตรวจจึงลืม
ไม่ได้: ลืมแล้วคอมไพล์ไม่ผ่าน

### ทุก credential มีสี่ด้านเหมือนกัน

```
receipt.claims        // สิ่งที่ผู้ออกพูด — คลังคำ ที่มี type
receipt.signature     // .valid
receipt.status        // .active และเหตุผลที่มันไม่ใช่
receipt.holder        // .bound — ใช่คนที่อยู่ตรงหน้าเราไหม
```

`claims` เป็น type ของ credential เอง ส่วนอีกสามอันเหมือนกันบนทุก credential
ในภาษานี้ เพราะมันคือสิ่งที่ trust policy ถูกเขียนถึง ทั้งสามอ่านได้ใน `trust`
และใน `verify` และไม่มีที่อื่น: แอปที่ตัดสินเองว่าลายเซ็นดีพอหรือยังคือสิ่งที่
`trust` มีอยู่เพื่อหยุด

### policy เป็นส่วนหนึ่งของ type

```
trust ReceiptFromMerchant(receipt: PurchaseReceipt) {
  anchor: "th.co.codefin.merchants"
  require {
    receipt.signature.valid
    receipt.status.active
    receipt.holder.bound
    receipt.claims.amount > 0
  }
}
```

ผลของการตรวจกับ policy นั้นมี type เป็น **`Verified<ReceiptFromMerchant>`** —
ชื่อ policy ไม่ใช่ชื่อ type ของ credential

นี่คือการแก้ที่สำคัญที่สุดในภาษานี้ `Verified<Employee>` แทบไม่มีค่าเลย: ข้อมูลที่
ตรวจกับ policy เข้มงวดกับข้อมูลที่ตรวจกับ `{ signature.valid }` จะมี type เดียวกัน
ฟังก์ชันที่เรียกร้อง `Verified<Employee>` จึงจะรับอันที่อ่อนกว่าไปอย่างเงียบๆ
และการรับประกันก็จะกลายเป็นของประดับ การใส่ชื่อ policy ลงใน type คือสิ่งที่ทำให้
มันเป็นจริง

type ของ credential ไม่ถูกระบุคู่ไปด้วยเพราะ policy กำหนดมันไปแล้ว พารามิเตอร์
สองตัวที่ขัดกันไม่ได้คือพารามิเตอร์สองตัวที่สุดท้ายจะถูกเขียนราวกับว่ามันขัดกันได้

**policy เป็นแบบ nominal** `Verified<A>` ไม่ใช่ `Verified<B>` ต่อให้ predicate
ของ A อนุมานไปถึงของ B การตัดสินการอนุมานระหว่าง predicate ตามอำเภอใจไม่ใช่สิ่งที่
คอมไพเลอร์ควรพยายามทำ และความสัมพันธ์ที่สำคัญก็ประกาศออกมาได้ (§11.4)

**ตัวประธานถูกผูกอย่างชัดแจ้ง** `receipt.signature.valid` ไม่ใช่
`signature.valid` เปลือกๆ: ผู้รับโดยปริยายไม่กำกวมจนถึงวินาทีที่มี credential
ตัวที่สองอยู่ใน scope พอดี

### ที่มาเดินทางไปกับตัวค่า

`Verified<P>` ครอบตัว credential มันไม่ครอบสิ่งที่คำนวณจากมัน และถ้าไม่มีส่วนนั้น
กระบวนทัศน์ก็หยุดอยู่แค่ขอบ: `amount / 100` เป็น `int` เหมือน int อื่นๆ และ
credential ที่แอปนี้เซ็นหลังจากนั้นก็ไม่ได้บอกอะไรเลยว่าตัวเลขของมันมาจากไหน

ดังนั้น **ทุกค่าพาชุดของ trust policy ที่มันสืบทอดมาไปด้วย** คอมไพเลอร์แพร่มัน
ต่อไปเอง และไม่มีใครเขียนมันด้วยมือยกเว้นที่ขอบสองจุด

```
credential.issue(LoyaltyMember {
  points: next.member.points from { ReceiptFromMerchant }
})
```

อนุประโยค `from` เป็นข้อเรียกร้อง ไม่ใช่คำอธิบายประกอบ: claim นี้คำนวณได้จาก
ข้อมูลที่ตรวจภายใต้ policy นั้นเท่านั้น และการผสมอะไรที่ยังไม่ตรวจเข้าไป — หรือที่
ตรวจภายใต้อย่างอื่น — คอมไพล์ไม่ผ่าน credential ที่ออกไปจึงพาที่มาของแต่ละ claim
ไปด้วย ตรวจได้ด้วยเครื่องโดยคนที่รับมันต่อ เขาไม่ต้องเชื่อลายเซ็นของเราเรื่องวิธี
ที่ตัวเลขนั้นถูกคำนวณ

ขอบที่สองคือ `prove` ซึ่งอนุประโยคนี้บอกว่าอะไรอยู่ในพยาน

**เรื่องนี้ยังจัดการได้เพราะแลตทิซเล็ก** มันไม่ใช่ลำดับชั้นของระดับความลับ
มันคือชุดของชื่อ policy และภาษาเป็น total ไม่มี recursion ไม่มี loop การแพร่จึง
เป็นการยูเนียนเซตในรอบเดียว

**มันยังใช้งานได้เพราะที่เหลือถูกอนุมานให้** error ชี้ไปที่บรรทัดที่ค่าซึ่งยังไม่
ตรวจเข้ามา ไม่ใช่บรรทัดที่มันถูกใช้ในที่สุด — อย่างหลังคือสิ่งที่ทำให้
information-flow type ขึ้นชื่อในทางไม่ดี

นี่เป็นชิ้นที่เสี่ยงที่สุดของระบบ type และมันมีทางถอยที่เรียงลำดับไว้: ทำใน
execution record ก่อน แล้วค่อยทำใน type ทีหลัง การทำให้ type เข้มขึ้นไม่ทำให้
โปรแกรมที่ถูกต้องอยู่แล้วพัง

## 5. Action

action เป็นสิ่งเดียวที่รันได้ และมันคือฟังก์ชัน:

```
(state ก่อนหน้า, input, บริบทตอนรัน, โค้ด) → (state ใหม่, output, effect)
```

การ replay การตรวจสอบย้อนหลัง และการแฮช state ล้วนตามมาจากลายเซ็นนั้น ไม่มีอะไร
อื่นในเอกสารนี้มีค่าเท่าไรถ้าไม่มีมัน

```
input → require → verify → compute → update → execute
```

เฟสถูกละได้แต่สลับลำดับไม่ได้

| เฟส | |
| --- | --- |
| **`input`** | สิ่งที่ action ได้รับมา |
| **`require`** | เงื่อนไขก่อนหน้าและการทำให้ type แคบลง |
| **`verify`** | trust policy |
| **`compute`** | การคำนวณแบบ pure |
| **`update`** | state ถัดไป |
| **`execute`** | effect — เฟสเดียวที่มี effect ปรากฏ |

### error เป็นผลลัพธ์ ไม่ใช่ค่า

ไม่มี `Result<T, E>` และไม่มีการส่งต่อ action ไม่มีที่ให้ส่งต่อไป: มันเป็น
ธุรกรรม และมันเกิดขึ้นหรือไม่เกิดขึ้น — type ของ error จึงจะต้องการการ return
ก่อนกำหนดทุกที่ ซึ่งเป็นการไหลของการควบคุมชุดที่สองในภาษาที่มีอยู่ชุดเดียว

สิ่งที่แอปต้องการจริงๆ คือวิธีปฏิเสธ **ด้วยเหตุผลของตัวเอง** ซึ่งไม่ใช่ทั้งสอง
ความล้มเหลวข้างบน:

```
compute {
  if (checked.claims.amount < 2_000) { refuse "tooSmallToEarn" }
}
```

`refuse` ระบุ key ใน text bundle ไม่ใช่ประโยค คนที่ถูกปฏิเสธเป็นคนอ่านมัน
มันจึงมาจากสิ่งที่ถูกเซ็นแล้ว — กฎเดียวกับทุกบรรทัดข้อความที่หน้าจอแสดง และเป็น
เหตุผลที่มันตรวจได้ตอน build

**มันอยู่ก่อน `execute`** พอถึงตรงนั้นชุด effect ถูกประกอบแล้วและ host กำลังจะ
ถูกยื่นให้ การปฏิเสธตอนนั้นเป็นการตัดสินใจที่สายเกินกว่าจะเป็นการตัดสินใจ

ดังนั้นจึงมีสี่ทางที่ action จะไม่ commit และมันเป็นคนละเรื่องกันสำหรับคนละคน:

| | ใครเห็น | มันแปลว่าอะไร |
| --- | --- | --- |
| `require` ไม่ผ่าน | ไม่มีใคร | ข้อบกพร่อง: แอปขอสิ่งที่มันไม่มีธุระจะขอ |
| `verify` ไม่ผ่าน | ผู้ใช้ | credential ปลอม เก่าเกินไป หรืออยู่นอก anchor |
| `refuse` | ผู้ใช้ | แอปปฏิเสธ ด้วยเหตุผลที่มันระบุชื่อไว้ |
| host ปฏิเสธทั้งชุด | ผู้ใช้ | ความยินยอมไม่ถูกให้ และไม่มีอะไรผิดพลาด |

### `require` กับ `verify` ล้มเหลวคนละแบบ และนั่นคือเหตุผลที่มีสองอัน

ทั้งคู่ปฏิเสธที่จะไปต่อและทั้งคู่ทำให้ type แคบลง การแยกทั้งสองด้วยวิธีที่มัน
*อ่าน* จะเป็นเรื่องรสนิยม การแยกด้วยวิธีที่มัน*ล้มเหลว*เป็นความต่างที่มีจริงและ
ทั้ง host และผู้ใช้ต้องการ:

- **`require` ล้มเหลวคือข้อบกพร่อง** แอปขอใช้แต้มที่มันเองได้ยืนยันไปแล้วว่า
  อาจไม่มี ไม่ควรมีใครเห็นข้อความเรื่องนี้ action ยกเลิก ไม่มีอะไร commit
  และมันควรไปอยู่ในรายงานบั๊ก
- **`verify` ล้มเหลวคือผลลัพธ์ปกติ** ใบเสร็จปลอม หมดอายุ หรือออกโดยคนนอก anchor
  ผู้ใช้ถูกบอกตรงๆ และแอปไม่ได้ทำอะไรผิด

แอปที่เอากติกาทางธุรกิจไปใส่ใน `require` จะได้การล้มในที่ที่มันอยากได้ข้อความ
และ error ควรจะบอกอย่างนั้น

ชื่อที่ประกาศใน `input` อยู่ใน scope ของทุกเฟสถัดไปแบบเปลือย — `receipt` ไม่ใช่
`input.receipt` เหมือนพารามิเตอร์ของฟังก์ชัน รากที่มีคำนำหน้าคือรากที่มาจากที่อื่น:
`state.` `context.` และ `next.` ใน `execute`

การทำให้แคบลงอยู่ใน `require` และสะกดออกมาเป็นคำ:

```
require {
  state.member exists
  amount > 0
}
```

ใช้ `exists` แทน `!= null` เพราะคนที่จำเป็นต้องอ่านบล็อกนี้ที่สุดคือคนที่มองว่า
`null` เป็นศัพท์เทคนิค มันเป็นคีย์เวิร์ดของเปลือก และเปลือกได้รับอนุญาตให้คิดใหม่

### `compute` เป็น pure และทุกฟังก์ชันก็เช่นกัน

```
function tierFor(points: int): Tier {
  return switch (points) {
    >= 10000 => Tier.gold,
    >= 2000  => Tier.silver,
    default  => Tier.bronze,
  }
}
```

กิ่งของ `switch` เป็นการเปรียบเทียบได้ การค้นหาจึงอ่านเหมือนตารางแทนที่จะเป็นโซ่
ของ `?:` ตัวดำเนินการเงื่อนไขยังอยู่สำหรับกรณีสองทาง ที่ตารางจะหนักกว่าสิ่งที่
มันมาแทน

**กิ่งถูกลองตามลำดับ และกิ่งที่ไปไม่ถึงเป็น error**

```
switch (points) {
  >= 2000  => Tier.silver,
  >= 10000 => Tier.gold,      // error: ไปไม่ถึง
  default  => Tier.bronze,
}
```

ภาษาที่ปฏิเสธ `default` เหนือ enum เพื่อความปลอดภัย จะปล่อยกิ่งที่ตายแล้วผ่านไป
อย่างเงียบๆ ไม่ได้ การขึ้นกับลำดับไม่เป็นไร การขึ้นกับลำดับที่ไม่มีใครเห็นสิไม่ได้

**ฟังก์ชันเป็น pure เสมอ ไม่มี effect polymorphism เพราะไม่มีฟังก์ชันที่มี effect
ให้ polymorphic ทับ** effect เป็นไวยากรณ์ อนุญาตเฉพาะภายใน `execute` และมันซ่อน
อยู่หลังการเรียกไม่ได้

ราคามีจริงและถูกยอมรับ: ลำดับ effect ที่ใช้ร่วมกันสาม action แยกเป็น helper
ไม่ได้ และต้องเขียนออกมาสามครั้ง สิ่งที่ได้แลกมาคือคำถาม "action นี้ทำอะไรได้บ้าง"
ตอบได้ด้วยการอ่านบล็อกเดียว ทั้งโดยคนและโดยเครื่องมือ โดยไม่ต้องไล่กราฟการเรียก
สำหรับภาษาที่มีอยู่เพื่อคำถามนั้น การแลกนี้ไม่ได้สูสีเลย

### `update` อธิบาย state ถัดไป

```
update {
  lifetimePoints: total
  member.points:  state.member.points + earned
  member.tier:    tier
}
```

**`update` เป็น patch ไม่ใช่นิพจน์** แต่ละบรรทัดระบุชื่อฟิลด์ของ state และค่าที่
มันจะเป็น ทุกอย่างที่ไม่ถูกระบุก็ไม่เปลี่ยน มันอ่านเหมือนตารางของสิ่งที่ action นี้
เปลี่ยน ซึ่งเป็นคำถามที่คนตรวจแอปกำลังถามพอดี

ใช้ `:` ไม่ใช่ `=` เพราะไม่มีอะไรถูกกำหนดค่า: บล็อกนี้อธิบาย state ถัดไป และ
state ก่อนหน้ายังอ่านได้ในชื่อ `state.…` ทางขวาของทุกบรรทัด path ระบุฟิลด์ซ้อนกัน
ได้ และมี index ของ list ไม่ได้ — นั่นคือจุดที่ patch จะต้องมีเรื่องของ optics
และคำตอบคือให้คำนวณ list ใหม่ใน `compute` แล้วมาระบุชื่อที่นี่ในบรรทัดเดียว

**เฉพาะ path ไม่มี record literal** `member: { ...state.member, tier: tier }`
พูดเรื่องเดียวกับ `member.tier: tier` และเป็นวิธีที่สองในการทำสิ่งเดียว ซึ่งเป็น
สิ่งที่ภาษานี้ใช้งบไปกับการหลีกเลี่ยง สร้าง record ใน `compute` แล้วมาระบุชื่อ
ที่นี่ถ้ามันเป็น record ใหม่ทั้งก้อนจริงๆ

บล็อกนี้ผลิต state ถัดไปและผูกมันไว้ในชื่อ **`next`** ซึ่ง `execute` เป็นคนอ่าน
ถ้าไม่มีการผูกนั้น แอปจะคำนวณเลขเดิมซ้ำในสองเฟส ทั้งสองจะเคลื่อนออกจากกันในวันที่
มีคนแก้อันใดอันหนึ่ง และ execution record ก็จะพิสูจน์ความไม่ตรงกันนั้นอย่างซื่อสัตย์

host commit state ถัดไป **ก็ต่อเมื่อ effect ใน `execute` สำเร็จ** — ทางเลือกอื่น
คือ state ที่บันทึกสิ่งที่ไม่ได้เกิดขึ้น ประโยคนั้นเรียกร้องอะไรจาก `execute`
อยู่ข้างล่าง

### `execute` คือที่ที่ effect ปรากฏ รวมถึงการเปิดเผย

```
execute {
  credential.issue(LoyaltyMember { points: next.member.points, … })

  present {
    disclose checked.claims.country
    prove checked.claims.birthdate <= context.time.now - duration(years: 20)
  }
}
```

**การเปิดเผยเป็น effect** มันยื่นข้อมูลของคนคนหนึ่งให้คนอื่น ซึ่งในระบบที่สร้าง
รอบความเป็นส่วนตัวคือสิ่งที่มีผลตามมามากที่สุดที่แอปทำได้ มันจึงต้องมี capability
ที่ประกาศไว้ ปรากฏใน `execute` พร้อมกับที่เหลือ และลงไปอยู่ใน execution record
ในฐานะ effect ไม่ใช่ในฐานะเชิงอรรถ

### `execute` ขอเป็นเซต ไม่ใช่ลำดับ

effect ใน `execute` เป็น **ชุดเดียว ยื่นไปพร้อมกัน** host อนุมัติทั้งชุดหรือ
ปฏิเสธทั้งชุด และ state จาก `update` ถูก commit ก็ต่อเมื่อชุดนั้นทำงานแล้ว
ไม่มี effect ไหนอ่านผลของอีกอันได้: ถ้าอันหนึ่งขึ้นกับผลของอีกอันจริงๆ นั่นคือ
สอง action และผู้ใช้ก็ได้เห็นทั้งสอง

นี่ไม่ใช่ความสะดวก ถ้าไม่มีมัน ประโยค "state commit ก็ต่อเมื่อ effect สำเร็จ"
เป็นประโยคที่รักษาไว้ไม่ได้: ออก credential แล้วเปิดเผยไม่สำเร็จ credential ก็
ออกไปแล้ว

**effect บางอย่างเอาคืนไม่ได้เลย** การเปิดเผยชัดที่สุด — ไม่มีปฏิบัติการไหนที่
ถอนรหัสไปรษณีย์ที่บอกไปแล้วคืนมา ดังนั้น:

- **หนึ่ง action เปิดเผยได้อย่างมากหนึ่งครั้ง** การเปิดเผยสองครั้งในชุดเดียว
  เป็นเงื่อนไขของการที่ทั้งชุดสำเร็จพร้อมกันไม่ได้ เพราะครั้งแรกเกิดขึ้นไปแล้ว
  ตอนที่ครั้งที่สองถูกปฏิเสธ
- **effect ที่ย้อนกลับไม่ได้ทำงานท้ายสุดในชุด** หลังทุกอย่างที่ host ยังถอยกลับได้
  คอมไพเลอร์เป็นคนจัดลำดับ ผู้เขียนไม่ต้องรู้

แอปที่อยากเปิดเผยสองครั้งคืออยากได้ความยินยอมสองครั้ง ซึ่งเป็นสิ่งที่สอง action
ให้มัน

`disclose` ยื่นค่าให้ ส่วน `prove` ยื่นคำตอบให้ `prove` ผลิต `Proof<bool>` และ
ไม่มีอะไรที่อ่อนกว่านั้น: **ในที่ที่ host ผลิต zero-knowledge proof จริงๆ ไม่ได้
คอมไพเลอร์ต้องปฏิเสธที่จะ build แอปนั้น** แทนที่จะถอยไปเปิดเผยวันเกิดแล้วเทียบ
ผู้เขียนเขียนว่า `prove` และจะไม่มีวันรู้เลยว่ามันไม่ได้เกิดขึ้น

### capability ระบุ type ไม่ใช่ string

```
capabilities {
  credential.read(PurchaseReceipt)
  credential.issue(LoyaltyMember)
  disclosure.present
}
```

type ของ credential ถูกประกาศในโปรแกรมเดียวกัน string ตรงนี้จะเป็นสำเนาที่สอง
ของชื่อที่ไม่ถูกตรวจ และคนที่เจอการพิมพ์ผิดครั้งแรกจะเป็นลูกค้า

## 6. Totality

**ทุกโปรแกรม VAL หยุด** ไม่มี recursion — กราฟการเรียกต้องไม่มีวัฏจักร และ
คอมไพเลอร์ตรวจมัน — และไม่มี loop ที่ไม่มีขอบเขต `List<T>` ถูกใช้ผ่าน combinator
ที่มีขอบเขตเท่านั้น:

```
map · filter · fold · any · all · count · first
```

แต่ละอันเดินบน list ที่มีอยู่แล้วและต่อความยาวมันไม่ได้ ความยาวของ list ที่รับเข้า
ถูกจำกัดโดย host

นี่เป็นจุดยืนที่ตั้งใจ ไม่ใช่ฟีเจอร์ที่ขาดไป สิ่งที่มันซื้อมา:

- **การหยุดโดยไม่ต้องมีเชื้อเพลิง** ขีดจำกัดเชื้อเพลิงของ Wasm (§8) กลายเป็น
  เข็มขัดเส้นที่สองแทนที่จะเป็นเส้นเดียว
- **ขอบเขตต้นทุนก่อนรัน** เครื่องมือตีราคา action ได้ และหน้าตัวอย่างค้างไม่ได้
- **ความ pure ที่มีค่าอยู่จริง** ฟังก์ชัน pure ที่อาจไม่คืนค่าเป็นการรับประกัน
  แค่ครึ่งเดียว

สิ่งที่มันเสีย: วันที่มีคนต้องการการวนซ้ำไม่จำกัดจริงๆ คำตอบคือเขากำลังเขียน
service ไม่ใช่แอป VAL คำตอบนั้นต้องเป็นจริงต่อไป ซึ่งแปลว่าต้องคอยดูว่าคนเอื้อมไป
หยิบอะไร

## 7. การรันและ record ของมัน

```
                        .val sources  (หนึ่ง package: หลายไฟล์ หนึ่ง scope)
                              │
        ┌─────────────────────┴─────────────────────┐
        │  front end — host รันทั้งหมดนี้เอง          │
        │                                           │
        │   lexer ─ parser ─ AST                    │
        │   การวิเคราะห์เชิงความหมาย                   │
        │   การตรวจ type          Verified<P>, T?, ที่มา
        │   การวิเคราะห์ capability                    │
        │   การวิเคราะห์ความเชื่อถือ                    │
        │   determinism + totality                  │
        │   การตรวจ policy                           │
        └─────────────────────┬─────────────────────┘
                              │
                    typed AST ┼ รายงาน capability   ← อนุมาน ไม่ใช่ประกาศ
                              │
                     IR ──────┴────── (v1 ข้ามขั้นนี้)
                      │
        ┌─────────────┴──────────────┐
        │  evaluator (v1)            │   เดิน typed AST
        │  Wasm back end (ทีหลัง)     │   เมื่อขีดจำกัดเชื้อเพลิงคุ้มค่า
        └─────────────┬──────────────┘
                      │
        sources + manifest + text bundle + รายงาน + assets
                      │
             แฮชความครบถ้วน ─ ลายเซ็น
                      │
                   .va package
                      │
              host runtime ─ แพลตฟอร์ม
```

**source เดินทางไปใน package** ไม่ใช่ "source หรือ bytecode" — ทั้งคู่ ในวันที่มี
bytecode เลย package ที่ host ตรวจซ้ำจากหลักการแรกไม่ได้ พาผู้เผยแพร่กลับไปสู่
ตำแหน่งที่ถูกเชื่อซึ่ง §1 เอาออกไป และแฮชของก้อนหนึ่งพิสูจน์แค่ว่ามันคือก้อนที่
ใครบางคนเซ็น ไม่ใช่ว่ามันคือโปรแกรมที่ใครบางคนอ่าน

สองขั้นไม่อยู่ในภาพนี้โดยตั้งใจ **เราไม่มี bytecode ของตัวเอง**: มี Wasm หรือ AST
และไม่มีอะไรอยู่ตรงกลาง (§8) และการปรับให้เหมาะสมก็ไม่มีกล่อง เพราะภาษาที่ total
และไม่มีการจองหน่วยความจำมีอะไรให้ปรับน้อยมาก และทุก pass เป็นอีกสิ่งที่ host
ต้องทำซ้ำให้ตรงเป๊ะ

### Determinism เป็นสมบัติของภาษา ไม่ใช่ของ runtime

ไม่มี `Date.now()` ไม่มี `random()` ไม่มี `fetch()` และไม่มีระบบไฟล์ **ในตัวภาษา**
ค่าที่ไม่แน่นอนมาจาก host ในบริบทตอนรันที่ประกาศชัด — `context.time.now`
`context.random.uuid` — และถูกบันทึกไปพร้อมกับทุกอย่างอื่น

### การเข้ารหัสแบบ canonical

แฮชของ state ของ input และของโค้ดต้องการการเข้ารหัสแบบ canonical หนึ่งเดียว
และต้องเป็นอันเดียวกันทุกที่: การทำ canonical ชุดที่สองคือสิ่งที่สองที่จะผิดแบบ
แนบเนียนได้ CBOR แบบ deterministic (dCBOR) คือรูปร่างที่ตั้งใจไว้ host ที่มีอยู่
แล้วก็จัดหามันผ่านอินเทอร์เฟซ แทนที่จะให้ภาษาพาคู่แข่งไปด้วย

### state เป็น Merkle tree ไม่ใช่ก้อนเดียว

execution record พา **ราก** ไปด้วย ไม่ใช่แฮชของ state ทั้งก้อน

ใบเป็นคู่ `(path, value)` — path เดียวกับที่ `update` แก้ อย่าง `member.tier`
และ `lifetimePoints` — แต่ละใบเข้ารหัสแบบ canonical เรียงตาม path แล้วประกอบเป็น
ต้นไม้ทวิภาคที่มีรูปร่างนิยามไว้ dCBOR ตรึงการเข้ารหัสของค่าและลำดับของฟิลด์ไว้
แล้ว จึงไม่ต้องคิดอะไรใหม่เพื่อให้สองการทำให้เกิดขึ้นตรงกัน

แฮชเดียวจะแปลว่าการพิสูจน์อะไรก็ตามเกี่ยวกับ state ต้องเปิดมันทั้งหมด นั่นตรงข้าม
กับสิ่งที่ภาษาส่วนที่เหลือทำ: credential เปิดเผย claim หนึ่งและพิสูจน์อีก claim
หนึ่งได้ ในขณะที่ state ของแอปเอง — ซึ่งเป็นที่ที่ "ระดับทอง" และ "มูลค่าพอร์ต"
อยู่จริงๆ — กลับเป็นก้อนตัน

เมื่อมีราก:

```
disclose state.member.tier
prove state.lifetimePoints >= 10_000
```

แต่ละอันเป็นการพิสูจน์การรวมอยู่เทียบกับรากที่อยู่ใน record อยู่แล้ว และการพิสูจน์
การรวมอยู่แบบ Merkle ภายในวงจรเป็นกลไกที่ใช้กันจนคุ้น เรื่องนี้จึงประกอบเข้ากับ
§10 ได้โดยไม่ต้องมีอะไรเป็นของตัวเอง

**proof เกี่ยวกับ state ไม่ใช่ proof เกี่ยวกับ credential และความต่างต้องไปถึง
ผู้ตรวจสอบ** claim ใน credential มีผู้ออกที่เซ็นมันหนุนหลัง ส่วนฟิลด์ใน state
มีเพียงห่วงโซ่ของ record ที่ผลิตมันหนุนหลัง — แอปยืนยันมันอย่างถูกต้องตามกติกาที่
ใครก็รันซ้ำได้ แต่ไม่มีบุคคลที่สามยืนหนุนหลังข้อมูลนำเข้า ที่มา (§4) พาเรื่องนี้
ไปด้วยโดยไม่ต้องมีกลไกใหม่: ค่าที่อนุมานจาก state ไม่มี trust policy ใดในเซตที่มา
ของมัน และผู้ตรวจสอบที่อ่าน proof เหนือเซตที่มาที่ว่างเปล่าก็กำลังถูกบอกผ่าน type
ว่าสิ่งนี้เป็นการยืนยันด้วยตัวเอง

**list มีหนึ่งใบต่อหนึ่งสมาชิก** รายการเดียวจึงถูกพิสูจน์ได้โดยไม่เปิดเผยเพื่อนบ้าน
ของมัน นั่นเปิดเผยความยาว ซึ่งมักไม่เป็นอันตรายและบางครั้งเป็น — จำนวนใบสั่งยา
จำนวนบัญชี ในที่ที่ความยาวเองอ่อนไหว ฟิลด์นั้นประกาศขอบเขตไว้และต้นไม้ถูกเติมให้
เต็มถึงขอบนั้น จำนวนใบจึงบอกแค่ว่า "ไม่เกินเท่านี้"

### Package

manifest โค้ด type credential capability assets เวอร์ชันของ runtime ความครบถ้วน
ลายเซ็น — ถูกเซ็นทั้งหมด มันตอบว่าใครเผยแพร่สิ่งนี้ เวอร์ชันไหนกำลังรัน
มันถูกแก้ไขหรือเปล่า มันทำอะไรได้ และอะไรกำลังทำงานอยู่

### package รายงานเกี่ยวกับตัวเอง และรายงานถูกอนุมาน

การคอมไพล์ผลิต **รายงาน capability**: สิ่งที่แอปนี้ทำกับผู้ใช้ได้ คำนวณจากโค้ด
แทนที่จะเขียนโดยผู้เขียนของมัน

ความต่างนี้คือคุณค่าทั้งหมด รายการสิทธิ์ของมือถือเป็นการประกาศ — นักพัฒนาเขียนเอง
มันหยาบ และภายในรายการนั้นแอปทำอะไรก็ได้ ส่วนอันนี้ถูกอนุมานโดยตัวตรวจ ผู้เผยแพร่
จึงพูดให้น้อยกว่าความจริงไม่ได้ และมันแม่นยำในแบบที่การประกาศเป็นไม่ได้:

```
reads          PurchaseReceipt.amount, PurchaseReceipt.purchased_at
               under ReceiptFromMerchant
discloses      nothing
proves         sum(Holding.market_value) >= 5_000_000_00   to broker.co.th
issues         LoyaltyMember, signed by th.co.codefin
talks to       broker.co.th
writes state   member, lifetimePoints
irreversible   none
```

ทุกบรรทัดในนั้นตอบได้แบบสถิต เพราะการตัดสินใจที่ทำไปด้วยเหตุผลอื่น: effect
ปรากฏเฉพาะใน `execute` ที่มาเดินตามค่า string ประกอบไม่ได้ ผู้รับสารถูกตรึงไว้ใน
manifest และภาษาเป็น total **ภาษาที่รายงานนี้คำนวณได้คือประเด็น ส่วนตัวรายงาน
เป็นแค่ที่ที่มันมองเห็นได้**

กฎสองข้อรักษาความซื่อสัตย์ของมัน:

- **host คำนวณมันใหม่และปฏิเสธเมื่อไม่ตรง** ผู้เผยแพร่ส่งสำเนามาเพื่อการตรวจและ
  เพื่อหน้าร้าน และมันไม่ใช่หลักฐานอะไรในตัวเอง — host เป็นเจ้าของตัวตรวจ (§1)
- **รายงานบอกข้อเท็จจริง host เป็นคนตัดสิน** ไม่มีคะแนนความเสี่ยงมาจาก package
  การเปิดเผยถูกอธิบายอย่างไร ดังแค่ไหน ด้วยคำอะไร และในภาษาไหน เป็นหน้าตาของ
  host ด้วยเหตุผลเดียวกับที่ใบยินยอมเป็น

**ใบยินยอมคือการเรนเดอร์รายงานนี้** ไม่ใช่เอกสารแยกที่ใครเขียนแล้วต้องคอยทำให้
ตรงกัน สิ่งที่ผู้ใช้อนุมัติกับสิ่งที่ตัวตรวจตรวจคือวัตถุเดียวกัน

แอปที่ประกาศ capability ซึ่งรายงานแสดงว่ามันไม่เคยใช้ คือ build ที่ล้มเหลว
ไม่ใช่คำเตือน ความยินยอมที่ขอไปเพื่อสิ่งที่ไม่ได้ใช้คือความยินยอมที่จ่ายไปเปล่าๆ
และมันฝึกให้คนตอบตกลง

### state อยู่นานกว่าโค้ดที่เขียนมัน

`version` อยู่บรรทัดแรกของทุกโปรแกรม และแอปที่เผยแพร่ไปแล้วจะถูกแทนที่ด้วยเวอร์ชัน
ถัดไป ในขณะที่ `state` ของใครสักคนยังนั่งอยู่บนเครื่องโดยถูกเขียนไว้ด้วยเวอร์ชันก่อน

**การเปลี่ยนรูปร่างของ `state` คือเวอร์ชันใหม่ และ state ของมันเริ่มจากว่างเปล่า**
ไม่มี migration ไม่มี compatibility shim ไม่มี dual reader นี่เป็นกฎเดียวกับที่
กำกับชนิดของแอปและ capability ของมันอยู่แล้ว: ผู้ใช้ยินยอมกับคำอธิบายหนึ่ง
คำอธิบายเปลี่ยน เขาจึงถูกถามใหม่ — และสิ่งที่เขาถูกถามอ่านเข้าใจได้ ก็เพราะไม่มี
state ที่สามที่เป็นครึ่งหนึ่งของแต่ละอัน

ทางเลือกอื่นแย่กว่าที่เห็น migration คือโค้ดที่รันกับข้อมูลที่เวอร์ชันปัจจุบัน
ไม่เคยผลิต ไม่มีใครใช้งานมันจริง และ replay จาก execution record ไม่ได้ เพราะไม่มี
action ไหนเป็นคนทำ ในภาษาที่ข้ออ้างทั้งหมดคือสิ่งที่รันไปพิสูจน์ได้ ขั้นตอนที่
พิสูจน์ไม่ได้ตรงรอยต่อระหว่างเวอร์ชันไม่ใช่ข้อยกเว้นเล็กๆ

แอปที่เสีย state ไปไม่ได้ควรเก็บมันในที่ที่ state ควรอยู่ — ใน credential ที่มัน
ออกให้ หรือบน backend ของมันเอง — แทนที่จะอยู่ในฟิลด์ที่มันเปลี่ยนชื่อได้เงียบๆ

### ไม่มีอะไรที่นี่เป็นฉันทามติ

สิ่งนี้คล้ายสัญญาอัจฉริยะและต่างกันในทางเดียวที่สำคัญ: state อยู่บนเครื่องเดียวและ
ไม่มีเครือข่ายไหนเห็นพ้องเกี่ยวกับมัน ห่วงโซ่ของรากเป็น **สิ่งที่ทำให้การแก้ไข
ปรากฏ ไม่ใช่สิ่งที่กันการแก้ไข** — คนหนึ่งทิ้งทั้งห่วงโซ่แล้วเริ่มใหม่ได้ และไม่มี
อะไรหยุดเขา สิ่งที่ห่วงโซ่ให้คือการตรวจจับ และให้เฉพาะกับคนที่เก็บ record ก่อนหน้า
ไว้เท่านั้น

นั่นไม่ใช่ข้อบกพร่องที่ต้องออกแบบให้หายไป มันคือผลของการที่ state เป็นของผู้ใช้เอง
สองอย่างทำให้มันพอในทางปฏิบัติ และไม่มีอย่างไหนต้องการโครงสร้างพื้นฐานใหม่:

- **ผู้ตรวจสอบจำรากล่าสุดที่มันเห็น** จากคนคนนี้ และปฏิเสธ record ที่ย้อนไป
  ก่อนหน้านั้น สิ่งนี้จับการย้อนกลับภายในความสัมพันธ์หนึ่ง ซึ่งเป็นที่ที่มูลค่าอยู่:
  โครงการสะสมแต้มที่จะถูกโกงคือโครงการที่คุยกับ wallet ใบนี้มาตลอด
- **credential ที่ออกไปบันทึกรากที่มันอนุมานมา** การย้อนกลับจึงทิ้ง credential
  ที่ถูกเซ็นแล้วชี้ไปยัง state ที่ไม่มีอยู่ในห่วงโซ่อีกต่อไป ซึ่งผู้ออกมองเห็น
  ผู้ออกกลายเป็นพยานของเวลาโดยไม่ถูกบอกว่า state บรรจุอะไร

**และ credential ถูกใช้ครั้งเดียว** การย้อนกลับแล้วสแกนใบเสร็จเดิมซ้ำคือการใช้ซ้ำ
และมันมีคู่กรณีเพียงรายเดียวที่มีสิทธิ์สนใจ — โครงการที่ออกแต้มนั้น คำตอบจึงไม่ใช่
บัญชีแยกประเภทแต่เป็น **nullifier** ที่ผู้ออกบันทึกไว้และปฏิเสธในครั้งที่สอง

มันต้องไม่ใช่ตัวระบุของ credential รายการของตัวระบุที่ใช้ไปแล้วเชื่อมทุกการยื่น
เข้ากับครั้งก่อนหน้า และทำลายความเชื่อมโยงไม่ได้ที่ระบบ proof ถูกซื้อมาเพื่อสิ่งนั้น
nullifier ถูก **คำนวณภายใน proof** จากความลับของผู้ถือและตัวระบุของโครงการแทน:
เป็น deterministic credential เดียวกันในโครงการเดียวกันจึงให้ค่าเดิมเสมอ และ
เชื่อมโยงไม่ได้ credential เดียวกันในอีกโครงการจึงให้ค่าที่ไม่เกี่ยวข้องกัน
มันมีราคาเป็นกลไกแฮชหนึ่งตัวในเซตย่อยที่พิสูจน์ได้ ไม่ใช่ทั้งสถาปัตยกรรม

transparency log สำหรับห่วงโซ่ทั้งเส้นของ wallet จะจับที่เหลือได้ มันเป็นส่วนประกอบ
ที่ต้องรันและเป็นช่องให้ metadata รั่ว และมันรอคนที่ต้องการมันจริงๆ

### ใครเซ็น credential ที่แอปออก

แอปไม่มีกุญแจผู้ออกและต้องไม่มี `credential.issue` จึงไม่ได้เซ็นอะไรเลย:
มันผลิตคำขอ effect เครื่องเซ็น execution record และ **backend ของผู้เผยแพร่ตรวจ
record นั้นแล้วเซ็น credential ด้วยกุญแจของตัวเอง**

นี่คือเหตุผลว่าทำไมผู้เผยแพร่ต้องมีเซิร์ฟเวอร์เลย และนี่คือทั้งหมดที่เซิร์ฟเวอร์ทำ:
มันไม่ได้รัน VAL ไม่ได้ถือ state และไม่เห็น state มันตรวจลายเซ็น แปลงแฮชของโค้ด
กลับไปเป็นเวอร์ชันที่มันเผยแพร่ ตรวจห่วงโซ่ความเชื่อถือ ตรวจ proof ถ้ามี —
กุญแจสำหรับตรวจอนุมานมาจากวงจรที่คอมไพล์แล้ว มันจึงรู้เองว่า predicate ไหนถูก
พิสูจน์แทนที่จะถูกบอก — แล้วจึงเซ็นหรือปฏิเสธ

การปฏิเสธคือประเด็น คนที่ถือเครื่องอยู่เขียน state ของตัวเองใหม่ได้ แต่เขาทำให้
ผู้เผยแพร่เซ็น credential ให้กับการรันที่ตรวจไม่ผ่านไม่ได้

ในที่ที่ credential ไม่มีมูลค่า รูปแบบที่อ่อนกว่าก็ใช้ได้: เครื่องเซ็นมันในความหมาย
ว่า "แอปนี้ เวอร์ชันนี้ บนเครื่องนี้" ซึ่งตรวจได้และเป็นการยืนยันด้วยตัวเอง
และมันก็บอกอย่างนั้น

### Execution record

ตัวระบุแอปและเวอร์ชัน ผู้เผยแพร่ แฮชของโค้ด action แฮชของ input **ราก** ของ state
ก่อนและหลัง policy ที่ใช้ capability ที่ใช้ effect ที่ขอและ effect ที่ทำไปแล้ว
— **รวมถึงการเปิดเผย** — บริบทตอนรัน ตราเวลา ลายเซ็น

## 8. เป้าหมายของการคอมไพล์

**ไม่มี VM ที่ทำขึ้นเอง ทั้งตอนนี้และต่อไป** ทุกอย่างที่ VM ที่สร้างเองจะให้ —
การกักบริเวณ ขีดจำกัดทรัพยากร ความเป็น deterministic ความพกพาได้ — Wasm ให้อยู่
แล้ว และการดูแลมันคือพันธะหลายปีกับส่วนของระบบที่ไม่ใช่ประเด็น

**v1 ไม่คอมไพล์เลย** มันเดิน typed AST ใน Rust: ไม่กี่ร้อยบรรทัด เป็น deterministic
และเป็นสิ่งที่ติดเครื่องมือวัดเพื่อทำ execution record ได้ง่ายที่สุดโดยห่างชั้น

การเก็บ source ไว้ใน package ไม่ใช่ทางเลือกเมื่อเรื่องนี้เกิดขึ้น — ดู §1
*ใครถูกเชื่อ* การมีแต่ bytecode จะแปลว่า host กำลังตรวจก้อนหนึ่งที่มีแต่ผู้เผยแพร่
เท่านั้นที่รับรองได้ว่ามันตรงกับ source ที่ถูกตรวจ

**ทั้งสองปลายอ่าน typed AST** ไม่มี IR อยู่ระหว่างกลาง และการเพิ่มเข้ามาก็คือการ
เพิ่มสิ่งที่สองที่ต้องคอยทำให้ซื่อตรงต่อสิ่งแรก back end ตัวที่สองถูกตรวจได้ทางเดียว:
มันต้องคำนวณสิ่งที่ตัวแรกคำนวณ บน source ชุดเดียวกัน

**Wasm คือปลายทาง ไปถึงเมื่อมีเหตุผล** — โค้ดของบุคคลที่สามที่ไม่ถูกเชื่อและ
ต้องการขีดจำกัดเชื้อเพลิงที่แข็งกับ bytecode ที่ถูกเซ็น front end ไม่เปลี่ยน
เปลี่ยนแค่ back end

- Wasm แกนกลางมีแค่ `i32`/`i64`/`f32`/`f64` เลี่ยงปัญหาตัวจองหน่วยความจำด้วยการ
  เก็บค่าไว้ **ฝั่ง host แล้วส่ง handle เป็น `i32`** พร้อม helper ที่ import เข้ามา
  (`val_field` `val_add` …) คอมไพเลอร์จึงปล่อยแค่การเรียกกับการไหลของการควบคุม
  และไม่มีอะไรอื่น ซึ่ง `wasm-encoder` ทำให้เป็นงานกลไก
- กฎห้าม float ใน §3 มีอยู่เพื่อเรื่องนี้เป็นหลัก
- การ trap เมื่อจำนวนเต็มล้นแมปเข้ากับ trap ของ Wasm ได้ตรงๆ
- **iOS ห้าม JIT** จึงต้องมี runtime แบบตีความ `wasmi` หรือ `wasm3` ภายในแกน
  Rust ครอบคลุม iOS Android และเดสก์ท็อปจากการผสานครั้งเดียว ส่วนเบราว์เซอร์ได้ฟรี
  ตรวจสถานะของ runtime เหล่านั้นและของ WasmGC ก่อนตัดสินใจ — เรื่องนี้ขยับเร็วกว่า
  ข้อกำหนดขยับ

## 9. ส่วนติดต่อผู้ใช้

แอปประกาศหน้าจอของมัน **มันไม่ได้ทำหน้าจอเอง** host เป็นผู้ส่งมอบ component
พฤติกรรมของมัน และ state ของมัน VAL บอกว่าใช้อันไหน จัดวางอย่างไร ผูกกับอะไร
และการกดเรียก action ไหน

```
screen Wallet {
  data {
    receipts: credentials of PurchaseReceipt verified with ReceiptFromMerchant
  }

  column {
    card(text: "balance", points: state.member.points)
    tabs {
      tab("history") { list(receipts) { r -> row(text: "receipt", at: r.claims.purchased_at) } }
      tab("rewards") { … }
    }
    button(text: "scan", emphasis: primary, onTap: ScanToEarn)
  }
}
```

### หน้าจออนุมานค่าได้ แต่ลงมือทำไม่ได้

ระหว่าง `data` กับการจัดวาง หน้าจอมีบล็อก **`compute`** ที่ใช้กติกาของ action:
pure ไม่มี effect เอื้อมไปถึง capability ไม่ได้

มันจำเป็นเพราะผลรวมเป็นฟังก์ชันของสิ่งที่อยู่บนหน้าจออยู่แล้ว และถ้าไม่มีมัน
ทุกหน้าจอที่มีผลรวมจะต้องเก็บผลรวมนั้นไว้ใน `state` — ถูกแฮช ถูกเซ็น ถูก replay
และคำนวณใหม่ได้จากข้อมูลที่หน้าจอถืออยู่แล้ว การเก็บค่าที่อนุมานได้ไว้ถาวรคือวิธีที่
ตัวเลขหนึ่งตัวสองสำเนาเริ่มไม่ตรงกัน

```
compute {
  const totalValue = holdings.fold(0) { sum, h -> sum + h.claims.market_value }
}
```

### การกดเรียก action และไม่มีอย่างอื่น

`onTap` ระบุชื่อ action ที่ประกาศไว้ ทุกการกดจึงผ่าน
`input → require → verify → compute → update → execute` ความยินยอมชุดเดียวกัน
execution record ชุดเดียวกัน **ส่วนติดต่อผู้ใช้ไม่ได้เพิ่มเส้นทางไปหา effect เลย**
— ไม่มีอะไรที่หน้าจอทำได้แล้ว action ทำไม่ได้ ซึ่งเป็นสิ่งที่ทำให้ §5 ยังจริงอยู่
เมื่อมีหน้าจอเข้ามา

### host เป็นเจ้าของ state ของการโต้ตอบ ทั้งหมด

แท็บไหนถูกเลือก list เลื่อนไปถึงไหน อะไรถูกพิมพ์ในช่องที่ยังไม่ได้ส่ง: ไม่มีอันไหน
เป็น state ของแอป มันไม่ถูกแฮช ไม่ถูก commit ไม่อยู่ใน execution record

กฎที่บังคับเรื่องนี้ไม่ใช่ความเรียบร้อย `state` ในภาษานี้ถูกแฮช ถูกเซ็น และ
replay ได้ ถ้าตำแหน่งการเลื่อนเข้าไปอยู่ในนั้น คำว่า "พิสูจน์ได้" ก็เจือจางลงทุก
ครั้งที่มีคนกด action ได้รับสิ่งที่ฟอร์มเก็บไว้ **ณ วินาทีที่มันถูกส่ง** ผ่าน
`input` ซึ่งเป็นกลไกที่มีอยู่แล้ว

ราคาคือแอปขับส่วนติดต่อผู้ใช้ของตัวเองไม่ได้ — มันสลับแท็บ ล้างช่องกรอก หรือเลื่อน
ไม่ได้ ยกเว้นผ่าน `navigate` ที่ประกาศไว้ นั่นเป็นการแลกแบบเดียวกับการไม่วาดเอง:
ยอมเสียการควบคุมเพื่อแลกกับพฤติกรรมที่ถูกต้องทุกที่ โดยไม่ต้องให้แต่ละแอปทำให้
ถูกต้องแยกกันเอง

### ไม่ใช่ทุกอย่างบนหน้าจอคือ credential

ราคา ข่าว แคตตาล็อก ประวัติธุรกรรม — ข้อมูลที่ดึงมาเพื่อดู การออก credential ให้
แต่ละอย่างจะไร้สาระ และปริมาณกับความผันผวนคือเหตุผลที่ชั้นนี้มีอยู่พอดี

```
screen Portfolio {
  data {
    holdings: credentials of Holding verified with FromLicensedBroker
    prices:   query broker.quotes(symbols: holdings.symbols) as List<Quote>
  }
}
```

**แอปยืนยันตัวตนด้วยการยื่น credential และไม่เคยแตะโทเคน** host เป็นผู้ยื่น
ขอ access token ยิงคำขอ และคืนแถวข้อมูลกลับมา แอปที่ถือ bearer token ไว้ส่งมันไป
ที่อื่นได้ และผู้ใช้ยินยอมให้มันถูกใช้ ไม่ได้ยินยอมให้มันถูกถือ

สิ่งที่เรื่องนี้เรียกร้อง:

- **ผู้รับสารอยู่ใน manifest ที่ถูกเซ็น** ไม่เคยประกอบตอนรัน — ซึ่ง string ทำ
  ไม่ได้อยู่แล้ว (§3)
- **การได้มาซึ่งสิทธิ์เข้าถึงเป็นการเปิดเผย** มันจึงประกาศ `disclosure.present`
  ปรากฏในความยินยอมที่ผู้ใช้ให้ และอยู่ใน execution record แถวข้อมูลที่กลับมา
  ไม่ใช่การเปิดเผย credential ที่ยื่นไปเพื่อให้ได้มันมาต่างหากที่ใช่
- ความยินยอมให้ครั้งเดียวต่อหนึ่งแอปและหนึ่งผู้รับสาร — "แอปนี้ทำการแทนคุณที่
  broker.co.th ได้ โดยแสดง credential บัญชีหลักทรัพย์ของคุณ" — ไม่ใช่ครั้งหนึ่ง
  ต่อการรีเฟรชหนึ่งครั้ง

### host ถือ session และทุกอย่างที่ตามมาจากนั้น

โทเคนเป็นของ host และทุกอย่างรอบมันก็เช่นกัน เขียนไว้เพราะแต่ละข้อเป็นจุดที่
ไม่อย่างนั้นแอปจะถูกเชื่อว่าจะประพฤติดี:

- **จำกัดขอบเขตต่อหนึ่งแอปและหนึ่งผู้รับสาร** สองแอปที่คุยกับโบรกเกอร์เดียวกัน
  ไม่มีอะไรร่วมกันเลย และการที่แอปเดียวเข้าถึงสองผู้รับสารคือการให้สิทธิ์สองครั้ง
- **ต่ออายุได้โดยไม่ต้องถามใหม่** ผู้ใช้ถูกถามครั้งเดียวว่าอะไรถูกเปิดเผย
  การต่ออายุไม่ได้เปิดเผยอะไรใหม่ เขาจะถูกถามอีกครั้งก็ต่อเมื่อสิ่งที่ต้องยื่น
  เปลี่ยนไป ซึ่งเป็นการเปลี่ยน manifest และจึงเป็นเวอร์ชันใหม่อยู่แล้ว
- **เก็บในที่ที่ host เก็บความลับ** ไม่เคยอยู่ใน state ของแอป ไม่เคยอยู่ใน
  package และ **ไม่เคยอยู่ใน execution record** record ถูกทำขึ้นเพื่อเอาไปแสดง
  ให้ใครสักคน โทเคนที่อยู่ในนั้นคือ credential ที่ยื่นให้ใครก็ตามที่อ่านมัน
  สิ่งที่ record พาไปคือข้อเท็จจริงว่ามีการยื่นต่อผู้รับสารรายนั้นเกิดขึ้น
- **ผู้ใช้เพิกถอนได้ ต่อแอปและต่อผู้รับสาร** จากนอกตัวแอป ในหน้าตาของ host ที่
  แอปวาดไม่ได้และเอื้อมไม่ถึง
- **ความล้มเหลวเป็นเรื่องที่ host เป็นคนรายงาน** แอปเห็นว่า query ไม่ตอบ ไม่ได้
  เห็นว่าเพราะอะไร — สิทธิ์ที่หมดอายุกับสิทธิ์ที่ถูกปฏิเสธหน้าตาเหมือนกันสำหรับมัน
  เพราะแอปที่แยกสองอย่างนี้ออกจะได้เรียนรู้บางอย่างเกี่ยวกับความสัมพันธ์ของผู้ใช้
  กับคนอื่น

### host แคชไว้ และบอกว่ามันเก่าแค่ไหน

คำตอบของ query ถูกเก็บไว้ใช้ตอนออฟไลน์ได้ **host เป็นคนแคชและ host เป็นคนแสดงอายุ
ของมัน** แอปไม่ได้เลือกทั้งสองอย่าง

เหตุผลคืออันเดียวกับที่ใช้กับราคาประเมินที่เก่าใน trust policy: ราคาจากสามชั่วโมง
ที่แล้วกับราคาสดต้องไม่หน้าตาเหมือนกัน และแอปคือฝ่ายที่มีผลประโยชน์ในการไม่พูดถึง
ความต่างนั้น

### ข้อมูลสามระดับ และ host เป็นคนวาดความต่าง

| ระดับ | มาจากไหน | ที่มา |
| --- | --- | --- |
| **ผู้ออกหนุนหลัง** | claim ใน credential | trust policy ที่มันถูกตรวจภายใต้ |
| **ยืนยันด้วยตัวเอง** | `state` ของแอปเอง | ว่างเปล่า แต่ยึดกับห่วงโซ่ของราก |
| **ต้นทางยืนยัน** | query ที่ตอบโดย API ที่ยืนยันตัวตนแล้ว | ผู้รับสารที่ตอบ |

อันที่สามไม่ใช่ว่าไม่มีอะไรเลย — host รู้แน่ชัดว่ามันยืนยันตัวตนกับต้นทางไหน
มันจึงพูดได้ว่า "จาก broker.co.th ไม่ได้ลงนาม" แทนที่จะพูดว่า "ยังไม่ตรวจสอบ"
แต่มันไม่ใช่ลายเซ็น และผู้ใช้ต้องมองออกว่าตัวเลขไหนบนหน้าจอมีคนยืนหนุนหลัง

**host เรนเดอร์ความต่าง และแอปเลือกวิธีไม่ได้** กฎเดียวกับหน้าตาของใบยินยอม:
แอปที่ทำให้ตัวเลขที่ดึงมาดูเหมือนมีผู้ออกหนุนหลังได้ จะทำลายคำสัญญาข้อเดียวที่
wallet ให้ไว้

### ข้อมูลที่ดึงมากับ record

ผลของ query **ไม่ถูก** บันทึก — execution record ที่เต็มไปด้วยพาดหัวข่าวจะกลบสิ่งที่
มันมีอยู่เพื่อพิสูจน์

แต่วินาทีที่ค่าแบบนั้นข้ามเข้าไปใน `compute` `update` `issue` หรือ `prove`
state ก็ขึ้นอยู่กับสิ่งที่ replay ไม่ได้ และห่วงโซ่ก็ไม่มีค่าอะไร ดังนั้น:
**ค่าที่ข้ามเส้นนั้นถูกบันทึกไว้ในบริบทตอนรัน** แบบเดียวกับข้อมูลนำเข้าจาก oracle
แล้วการ replay ก็ทำงานได้อีกครั้ง

คอมไพเลอร์บอกได้ว่าอันไหนเป็นอันไหน เพราะที่มาติดตามมันอยู่แล้ว — และ
`from { … }` บน claim ที่ออกไป (§4) ปฏิเสธการข้ามเส้นนั้นตรงๆ ในที่ที่ claim
ประกาศ policy ที่ไม่มี query ไหนทำให้พอใจได้

### แม่แบบสำเร็จรูปกับการประกอบเองเป็นระบบเดียวกัน

host ส่งมอบ **แม่แบบ** — หน้าจอแบบรายการ แบบรายละเอียด แบบฟอร์ม แบบมีแท็บ —
และแอปจะใช้อันหนึ่ง หรือประกอบของตัวเองจาก primitive ชุดเดียวกันก็ได้

มันไม่ใช่สองกลไก **แม่แบบคือการประกอบที่ host เขียนไว้** ในข้อมูลชุดเดียวกัน
เรนเดอร์โดยตัวเรนเดอร์เดียวกัน ทำเวอร์ชันแบบเดียวกัน ความหมายชุดเดียว และ host
ก็กำลังใช้สิ่งที่มันส่งมอบเอง

การประกอบเองได้รับอนุญาตเพราะไม่อย่างนั้นทุกแอปจะหน้าตาเหมือนกันหมด และผู้เขียน
แคตตาล็อกก็จะกลายเป็นคอขวดของผลิตภัณฑ์ของคนอื่นทั้งหมด

### แคตตาล็อกมีเวอร์ชัน และ package ระบุเวอร์ชันของมัน

แอปที่เซ็นกับแคตตาล็อก v1 จะไปรันบน host ที่ส่งมอบ v3 **package บันทึกเวอร์ชัน
แคตตาล็อกที่มันถูก build ด้วย และ host เรนเดอร์ความหมายชุดนั้นหรือไม่ก็ปฏิเสธที่
จะรันมัน**

เรื่องนี้จ่ายไหวก็เพราะส่วนติดต่อผู้ใช้เป็นข้อมูล: การรักษาความหมายของ component
เก่าเป็นการตัดสินใจเรื่องการเรนเดอร์ ในขณะที่การรักษาโค้ดเก่าจะเป็นภาระการดูแลที่
ไม่มีวันจบ มันไม่ฟรี — ทุกเวอร์ชันคือเส้นทางการเรนเดอร์เพิ่มอีกหนึ่งเส้น — และ
ผู้เขียนแคตตาล็อกควรรู้สึกถึงราคานั้น เพราะเขาคือคนที่ตัดสินว่ามันเปลี่ยนบ่อยแค่ไหน

### อิสระในการประกอบ ไม่ใช่ในเรขาคณิต

- **prop เชิงความหมายเท่านั้น** — `text:` (key ใน manifest) `icon:` (จาก
  แคตตาล็อก) `emphasis:` `state:` `onTap:` ไม่มีสี ไม่มีฟอนต์ ไม่มีขนาดพิกเซล
  ระยะห่างมาจากสเกล
- **ไม่มีการวางตำแหน่งสัมบูรณ์** คอนเทนเนอร์เป็นเจ้าของการล้นของตัวเอง
- **ข้อความถูกวัดและตัดบรรทัดโดย host** เพราะมันมาจาก manifest และเพราะภาษาไทย
  ยาวกว่าอังกฤษราวหนึ่งในสาม

การประกอบเองคือจุดที่ระบบออกแบบมักเริ่มพังบนจอเล็ก ข้อความยาว และธีมมืด คำตอบ
ไม่ใช่การห้าม:

### การจัดวางถูกตรวจตอน build

ส่วนติดต่อผู้ใช้เป็นข้อมูลและภาษาเป็น total เครื่องมือจึงเรนเดอร์ทุกหน้าจอในทุก
ขนาด ทุกภาษา และทุกธีม **ก่อนที่มันจะถูกปล่อย** และ build ล้มเหลวถ้ามีอะไรล้น
หรือคอนทราสต์ต่ำกว่าเกณฑ์

แอปที่ประกอบหน้าจอเองและหน้าตาไม่เหมือนแอปอื่นคือแอปที่ทำงานตามที่ตั้งใจ ส่วนแอป
ที่ประกอบหน้าจอเองแล้วพังบนมือถือเครื่องเล็กในภาษาไทยจะไม่ได้ถูกเผยแพร่

"ตอน build" หมายถึง build ของ host ไม่ใช่ของผู้เผยแพร่ ผู้เผยแพร่ที่ข้ามเครื่องมือ
ของเราไปไม่ได้ข้ามอะไรเลย: ส่วนติดต่อผู้ใช้เป็นข้อมูลที่อยู่ใน package และการตรวจ
ถูกรันใหม่ก่อนแอปจะถูกรับเข้า

### ข้อความมาจาก manifest ตรวจโดยคอมไพเลอร์

```
"balance": { th: "คุณมี {points} แต้ม", en: "You have {points} points" }

card(text: "balance", points: state.member.points)
```

คอมไพเลอร์อ่าน manifest — ทั้งสองถูกเซ็นเป็น package เดียว การตรวจแยกกันจึงจะ
เท่ากับการเซ็นการจับคู่ที่ไม่มีใครตรวจ — และปฏิเสธ key ที่หายไป ช่องที่หายไป
ช่องที่ผิด type **และภาษาที่ยังไม่ได้แปล** ภาษาของตลาดหนึ่งที่ขาดไปคือ build ที่
ล้มเหลว ไม่ใช่รายงานบั๊ก

ตัวเลข วันที่ และสกุลเงินถูกจัดรูปแบบโดย host ตามภาษา แอปทำเลขไทยหรือวันที่
พุทธศักราชผิดไม่ได้ เพราะมันไม่เคยแตะสิ่งเหล่านั้น

### สิ่งที่เป็นจริงไม่ว่าอย่างไร

- **ใบยินยอมเป็นหน้าตาของ host** ไม่มีแอปไหนวาดมัน บังมัน หรือเลียนแบบมัน
- **แบรนด์มาจาก manifest ที่ถูกเซ็น** ไม่เคยมาจากการจัดรูปแบบ
- **UI เป็นข้อมูล ไม่ใช่โค้ด** — ถูกเซ็น ถูก diff และถูกตรวจสอบด้วยการเข้ารหัส
  แบบ canonical ชุดเดียวกับ execution record
- **ไม่มีการวาดตามอำเภอใจเด็ดขาด** ผู้เผยแพร่ที่ต้องการพิกเซลต้องการชั้น webview
  และจ่ายค่ามันด้วย capability ที่ชั้นนั้นมีไม่ได้

## 10. Proof

`prove` คอมไพล์ลงไปเป็นวงจร นั่นเป็นไปได้กับส่วนเสี้ยวหนึ่งของภาษาเท่านั้น และ
**คอมไพเลอร์ต้องรู้ว่าส่วนเสี้ยวไหน** เพราะกฎใน §5 — ที่ว่า proof ต้องไม่เสื่อม
ลงเป็นการเปิดเผยอย่างเงียบๆ — รักษาไว้ไม่ได้ด้วยคอมไพเลอร์ที่รู้ตอนกำลังพิสูจน์

จึงมี **เซตย่อยที่พิสูจน์ได้** ตรวจแบบสถิต และการออกนอกเซตนั้นเป็น error ที่มี
ข้อความบอกว่าบรรทัดไหนและเพราะอะไร

ภายในเซตนั้น:

- จำนวนเต็มที่ประกาศความกว้าง — `int<32>` — เพราะการตรวจช่วงค่าเป็นต้นทุนหลัก
  และมันแปรตามจำนวนบิต
- `date` และ `datetime` ในฐานะจำนวนเต็ม เทียบกัน
- การเท่ากันของ string ไม่มีการประกอบ ซึ่ง §3 ห้ามไว้ทุกที่อยู่แล้ว
- `switch` และ `?:` โดยจ่ายค่าของ **ทุก** กิ่ง ไม่ใช่กิ่งที่ถูกเลือก — เรื่องนี้
  ต้องพูดออกมา ไม่อย่างนั้นจะไม่มีใครเข้าใจว่าทำไม proof ถึงช้า
- list combinator ที่รู้ความยาวตอนคอมไพล์
- **nullifier** คำนวณจากความลับของผู้ถือและตัวระบุของโครงการ — ดู §7
- **การรวมอยู่แบบ Merkle เทียบกับรากของ state** proof จึงเป็นเรื่องของ state
  ได้เช่นเดียวกับเป็นเรื่องของ claim — โดยความต่างเรื่องที่มาใน §7 ไปถึงผู้ตรวจสอบ
  แทนที่จะถูกยุบรวมเป็นคำว่า "ตรวจแล้ว"

ภายนอกเซตนั้น: effect และอะไรก็ตามที่ไม่รู้ขนาดแบบสถิต

สิ่งที่ host จัดหา และ VAL ไม่ได้จัดหา: วงจรที่พิสูจน์ว่า claim มาจาก credential
ที่ผู้ออกซึ่งไล่ถึง anchor ได้เป็นคนเซ็น VAL ให้ predicate เหนือ claim เหล่านั้น
และทั้งสองประกอบกันบนพยาน `disclose` ทำเครื่องหมายข้อมูลนำเข้าสาธารณะ ทุกอย่างอื่น
ที่ proof แตะเป็นพยาน ความสุ่มที่ใช้ในการพิสูจน์ไม่เคยเข้าไปใน execution record
— ข้อความที่ยืนยันกับคำวินิจฉัยต่างหากที่เข้าไป

## 11. คำถามที่ยังเปิดอยู่

1. **host ต้องจัดหาอะไรบ้างกันแน่** ถูกเอ่ยถึงตลอดเอกสารนี้และไม่ถูกระบุไว้ที่ไหน
   เลย และตอนนี้มันครอบคลุมห้าเรื่องแทนที่จะเป็นเรื่องเดียว: capability
   text bundle แคตตาล็อก component การจัดการ session และโทเคน และขอบเขตของขนาด
   ค่าที่ totality ไม่ครอบคลุม การเขียนมันลงไปคือบททดสอบที่ซื่อสัตย์ว่า host
   รายแรกรั่วเข้ามาในตัวภาษาหรือยัง และไม่มีอะไรเกี่ยวกับ host รายที่สองเป็นจริง
   จนกว่ามันจะมีอยู่
2. **`type` ถูกประกาศใน §2 และไม่ถูกระบุไว้ที่ไหนเลย** record ธรรมดามีอยู่ สิ่งที่
   ยังไม่ลงตัวคือมันถือฟิลด์ที่ตรวจแล้วกับยังไม่ตรวจเคียงกันได้ไหม ซึ่งเป็นคำถาม
   เรื่องที่มา (§4) ไม่ใช่คำถามเรื่องไวยากรณ์

ทุกข้ออื่นที่เคยมีหมายเลขอยู่ตรงนี้ลงตัวแล้วและถูกย้ายเข้าไปในเนื้อความ

## 12. ลำดับงาน

1. parser และ typed AST สำหรับเปลือกกับนิพจน์
2. ตัวตรวจ type: `Verified<P>` ความเป็น null ได้ การ switch อย่างครบถ้วน
   เลขคณิตที่ trap ตำแหน่งของ effect กราฟการเรียกที่ไม่มีวัฏจักร
3. การวิเคราะห์ capability และความเชื่อถือเหนือ typed AST
4. evaluator แบบเดินต้นไม้ คำขอ effect execution record — ที่มาอยู่ใน record
   ก่อน แล้วค่อยอยู่ใน type ทีหลัง
5. อินเทอร์เฟซของ host (§11.1) และหนึ่ง capability ที่ต่อครบตั้งแต่ต้นจนจบ
6. หน้าจอ: แม่แบบที่มีอยู่แล้วในฐานะ UI ของ host จากนั้นการประกอบ แล้วจึงเป็น
   การตรวจการจัดวางตอน build
7. ทุกอย่างที่เหลือ — Wasm back end เซตย่อยที่พิสูจน์ได้ การทำ package — หลังจาก
   มีแอปจริงและมันดันเข้ามา
