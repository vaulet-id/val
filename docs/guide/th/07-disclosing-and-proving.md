# การเปิดเผยและการพิสูจน์

สองเรื่องที่ต่างกัน และความต่างนั้นคือเหตุผลที่แพลตฟอร์มนี้มีอยู่

```val
execute {
  present {
    disclose checked.claims.country
    prove checked.claims.birthdate <= context.time.now - duration(years: 20)
  }
}
```

**`disclose` ยื่นค่าให้** เขาได้รู้ประเทศ

**`prove` ยื่นคำตอบให้** เขาได้รู้ว่าคนคนหนึ่งอายุเกินยี่สิบ เขาไม่ได้รู้วันเกิด
และคำนวณย้อนกลับทีหลังไม่ได้

## prove ไม่ใช่การเปรียบเทียบที่คุณทำเอง

วิธีทำ age check ที่นึกออกทันทีคืออ่านวันเกิดแล้วเปรียบเทียบ นั่นคือการเปิดเผย
ที่ตามด้วยการเปรียบเทียบ — คุณเห็นวันที่นั้นแล้ว และผู้ดูแลประตูก็ได้แต่เชื่อใจ
ว่าคุณจะไม่เก็บมันไว้

`prove` ผลิต `Proof<bool>` และไม่มีอะไรที่อ่อนกว่านั้น ในที่ที่ host ผลิต
zero-knowledge proof จริงๆ ไม่ได้ **แอปของคุณ build ไม่ผ่าน** มันไม่ถอยไปเปิดเผย
วันเกิดแล้วเปรียบเทียบให้ เพราะคุณเขียนว่า `prove` และคุณจะไม่มีวันรู้เลยว่ามัน
ไม่ได้เกิดขึ้น

## ทั้งคู่เป็น effect

การเปิดเผยต้องใช้ `disclosure.present` ปรากฏใน `execute` พร้อมกับอย่างอื่น และ
ลงไปอยู่ใน execution record การยื่นข้อมูลของใครสักคนให้บุคคลที่สามคือสิ่งที่มี
ผลตามมามากที่สุดที่แอปที่นี่ทำได้ มันไม่ใช่เชิงอรรถ

**หนึ่งการเปิดเผยต่อหนึ่ง action** effect ใน `execute` เป็นชุดเดียว และไม่มีอะไร
ถอนรหัสไปรษณีย์ที่บอกไปแล้วคืนมาได้ — การเปิดเผยครั้งที่สองจึงเป็นเงื่อนไขต่อจาก
ชุดที่ครั้งแรกทำเสร็จไปแล้วไม่ได้ สองการเปิดเผยต้องการความยินยอมสองครั้ง
ซึ่งก็คือสอง action

## อะไรที่พิสูจน์ได้

`prove` คอมไพล์ลงไปเป็นวงจร และมีแค่ส่วนเสี้ยวหนึ่งของภาษาที่ทำได้ คอมไพเลอร์
บอกคุณตอนที่คุณออกนอกส่วนนั้น ซึ่งเป็นทางเดียวที่คำสัญญาข้างบนจะรักษาไว้ได้ —
กฎที่ค้นพบตอนกำลังพิสูจน์ ไม่ใช่กฎ

ในส่วนนั้นมี: จำนวนเต็มที่ประกาศความกว้างไว้ วันและเวลาที่เทียบกันแบบจำนวนเต็ม
การเท่ากันของ string `switch` และ `?:` และ list combinator ที่รู้ความยาวตอน
คอมไพล์ ซึ่งก็คือสิ่งที่ `limit` ในการประกาศ `data` มีไว้เพื่อการนั้น

สองเรื่องที่ควรรู้ก่อนเขียน:

**ทุกกิ่งมีราคา** วงจรจ่ายให้ทั้งสองข้างของเงื่อนไข ไม่ใช่ข้างที่ถูกเลือก
`?:` ที่ดูราคาถูกคือการคำนวณสองชุด

**มันจ่ายตามขอบเขต ไม่ใช่ตามข้อมูล** proof เหนือ list ที่ยาวไม่เกิน 200 จ่าย
ค่าบวก 200 ครั้ง ไม่ว่าผู้ใช้จะถือสองรายการหรือสองร้อยรายการ ซึ่งก็เป็นเหตุผล
เดียวกับที่มันไม่รั่วว่าเขาถืออยู่กี่รายการ

## การพิสูจน์เหนือ state ของคุณเอง

คุณพิสูจน์เรื่องของ `state` ได้ด้วย — มันเป็น Merkle tree ฟิลด์เดียวจึงแสดงได้
โดยไม่ต้องเปิดที่เหลือ

แต่ให้รู้ว่าคุณกำลังอ้างอะไร claim ใน credential มีผู้ออกที่เซ็นมันไว้หนุนหลัง
ส่วนฟิลด์ใน state มีห่วงโซ่ของ record ที่ผลิตมันขึ้นมาหนุนหลัง: แอปของคุณยืนยัน
มันอย่างถูกต้อง ตามกติกาที่ใครก็ตามรันซ้ำได้ และ **ไม่มีบุคคลที่สามยืนหนุนหลัง
ข้อมูลนำเข้า** ผู้ตรวจสอบถูกบอกว่าเขากำลังดูอันไหนในสองอันนั้น และมันไม่ใช่
ข้อเท็จจริงเดียวกัน

## อะไรที่พิสูจน์ไม่ได้

อะไรก็ตามที่มาจาก API คำตอบของ query เป็นคำพูดของใครคนหนึ่ง ไม่ใช่ลายเซ็นของใคร
และ proof เหนือมันจะดูแข็งแรงเท่ากับ proof เหนือ credential ทั้งที่ไม่ได้เป็น
แบบนั้นเลย คอมไพเลอร์ปฏิเสธมัน และทางเลือกที่เหลือก็ซื่อสัตย์: เปิดเผยตัวเลขนั้น
แล้วบอกว่ามันมาจากไหน
