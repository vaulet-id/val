# Action

action เป็นสิ่งเดียวที่รัน มันคือฟังก์ชัน:

```
(state ก่อนหน้า, input, บริบทตอนรัน, โค้ด) → (state ใหม่, output, effect)
```

ทุกอย่างที่เหลือในภาษานี้มีอยู่เพื่อให้ลายเซ็นนั้นเป็นจริง — ซึ่งเป็นสิ่งที่ทำให้
การรันหนึ่งครั้ง replay ได้ และการรันที่ replay ได้เป็นแบบเดียวที่พิสูจน์ได้

```
input → require → verify → compute → update → execute
```

จะละอันไหนก็ได้ แต่ห้ามสลับลำดับ

## สี่ทางที่ action ไม่ commit

มันเป็นคนละเรื่องกันสำหรับคนละคน และการเลือกผิดคือความผิดพลาดที่พบบ่อยที่สุด
ในแอปตัวแรก

| | ใครเห็น | ใช้เมื่อไหร่ |
| --- | --- | --- |
| `require` ไม่ผ่าน | ไม่มีใคร | สิ่งที่ไม่ควรเป็นเท็จเลย ถ้าเป็นเท็จคือบั๊กของคุณ |
| `verify` ไม่ผ่าน | ผู้ใช้ | credential ปลอม เก่าเกินไป หรืออยู่นอก anchor ของคุณ |
| `refuse "key"` | ผู้ใช้ | กติกาของคุณเอง: น้อยไป เร็วไป หรือรับไปแล้ว |
| host ปฏิเสธ | ผู้ใช้ | เขาตอบว่าไม่ |

กติกาทางธุรกิจที่เขียนใน `require` ให้ผลเป็นการล้มทั้งที่คุณอยากได้ข้อความ
ส่วนบั๊กที่เขียนใน `refuse` ทำให้ใครสักคนได้อ่านประโยคสุภาพเกี่ยวกับความผิดพลาด
ของคุณ

## ประกาศไว้ไม่ได้ผูกอะไร

action เกิดขึ้นเพราะมีคนกดอะไรบางอย่าง ถ้าไม่มีหน้าจอไหนใน package ระบุชื่อมัน
ไว้ใน `onTap` ก็ไม่มีอะไรไปถึงมันได้ — และคอมไพเลอร์บอกอย่างนั้น เพราะ
**capability ที่มันต้องใช้ยังอยู่บนใบยินยอมที่ผู้ใช้ตกลงไปแล้ว**

action อยู่ไฟล์หนึ่งแล้วถูกกดจากหน้าจอในอีกไฟล์ได้: package คือ scope เดียว
ส่วน package ที่ไม่มีหน้าจอเลยคือชิ้นส่วนที่รอส่วนที่เหลือของตัวเอง และถูกปล่อยไว้เฉยๆ

## `input`

```val
input {
  receipt: Credential<PurchaseReceipt>
}
```

ชื่อที่ประกาศตรงนี้อยู่ใน scope ของทุกเฟสถัดไป แบบเปลือยๆ — `receipt` ไม่ใช่
`input.receipt` เหมือนพารามิเตอร์ของฟังก์ชัน

## `require`

เงื่อนไขก่อนหน้า และการทำให้ type แคบลง:

```val
require {
  state.member exists
  amount > 0
}
```

ใช้ `exists` แทน `!= null` เพราะคนที่จำเป็นต้องอ่านบล็อกนี้ที่สุดคือคนที่มองว่า
`null` เป็นศัพท์เทคนิค จนกว่าคุณจะบอก การอ่านทะลุ `state.member` เป็น type error
ไม่ใช่การล้มทีหลัง

## `verify`

trust policy และเป็นที่เดียวที่ credential กลายเป็นของที่ใช้ได้ หลายนิพจน์ถูก
AND เข้าด้วยกันโดยปริยาย

## `compute`

pure ไม่มี effect และ **ไม่มี effect ไหนซ่อนอยู่หลังฟังก์ชันได้** — ทุก
`function` ในภาษานี้เป็น pure จึงไม่มี helper ที่มี effect ให้เรียก

นั่นมีราคาจริง: ลำดับ effect ที่ใช้ร่วมกันสาม action ต้องเขียนออกมาสามครั้ง
สิ่งที่ได้แลกมาคือคำถาม "action นี้ทำอะไรได้บ้าง" เป็นบล็อกเดียวที่อ่านได้จบ
แทนที่จะเป็นกราฟการเรียกที่ต้องไล่ตาม สำหรับภาษาที่มีอยู่เพื่อคำถามนั้นทั้งภาษา
การแลกนี้ไม่ได้สูสีเลย

เลขคณิตที่นี่ trap ไม่ใช่ wrap การล้นและการหารด้วยศูนย์หยุด action เพราะตัวเลข
ที่ผิดแล้ว execution record ก็ไปพิสูจน์มันอย่างซื่อสัตย์ แย่กว่าการล้มเหลว

## `update`

เป็น patch ไม่ใช่นิพจน์:

```val
update {
  lifetimePoints: total
  member.points:  state.member.points + earned
  member.tier:    tier
}
```

แต่ละบรรทัดระบุฟิลด์และค่าที่มันจะเป็น อะไรที่ไม่ถูกระบุก็ไม่เปลี่ยน ใช้ทวิภาค
ไม่ใช่ `=` — ภาษานี้ไม่มีการกำหนดค่าที่ไหนเลย — และ state ก่อนหน้ายังอ่านได้ในชื่อ
`state.…` ทางขวาของทุกบรรทัด

path ซ้อนกันได้ แต่มี index ของ list ไม่ได้ ถ้าคุณต้องการ list ใหม่ ให้สร้างใน
`compute` แล้วมาระบุชื่อที่นี่ในบรรทัดเดียว

## `execute`

ที่เดียวที่ effect ปรากฏ และมันไม่ได้ลงมือทำ:

```val
execute {
  credential.issue(LoyaltyMember { points: next.member.points })
}
```

`next` คือ state ที่ `update` ผลิตออกมา การคำนวณเลขเดิมซ้ำตรงนี้แทน คือวิธีที่
ตัวเลขหนึ่งตัวสองสำเนาเริ่มไม่ตรงกัน

**effect ตรงนี้เป็นชุดเดียว** host เอาไปทั้งหมดหรือไม่เอาเลย และ state ของคุณ
commit ก็ต่อเมื่อมันเอาไป ไม่มี effect ไหนอ่านผลของอีกอันได้ — ถ้าอันหนึ่งขึ้นกับ
ผลของอีกอันจริงๆ นั่นคือสอง action และผู้ใช้ก็ได้เห็นทั้งสอง

effect ที่ย้อนกลับไม่ได้ถูกจัดไว้ท้ายสุดโดยอัตโนมัติ และหนึ่ง action เปิดเผยข้อมูล
ได้ **อย่างมากหนึ่งครั้ง** เพราะไม่มีอะไรถอนรหัสไปรษณีย์ที่บอกไปแล้วคืนมาได้
การเปิดเผยครั้งที่สองจึงเป็นเงื่อนไขต่อจากชุดที่ครั้งแรกทำเสร็จไปแล้วไม่ได้
