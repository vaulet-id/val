# State และเวอร์ชัน

```val
state {
  member:         LoyaltyMember?
  lifetimePoints: int default 0
}
```

เป็นของคุณ อยู่บนเครื่องเขา เปลี่ยนได้โดย `update` ใน action เท่านั้น ใช้
`default` ไม่ใช่ `=` — ภาษานี้ไม่มีการกำหนดค่า และการยกเว้นหนึ่งข้อในการประกาศ
state ที่คงอยู่ถาวรคือที่ที่แย่ที่สุดที่จะเก็บข้อยกเว้นนั้นไว้

## มันถูกแฮช และนั่นคือประเด็น

หลังทุก action host สร้าง Merkle tree เหนือใบ `(path, value)` ของ state คุณ
แล้วบันทึกรากไว้ record ของ action ถัดไปพารากก่อนหน้าไปด้วย ทั้งสองจึงต่อกันเป็น
ห่วงโซ่: การเขียน state ทับโดยไม่รัน action ที่ผลิตมันขึ้นมาใหม่ ทำให้ห่วงโซ่ขาด
ทันทีที่ action ถัดไปรัน

นั่นไม่ใช่การ*กันการแก้ไข* state อยู่บนเครื่องของใครสักคน และเขาโยนทิ้งทั้งก้อน
ได้ — นี่ไม่ใช่บล็อกเชน ไม่มีใครอื่นถือสำเนา และการทำเป็นว่าใช่คือการให้สัญญาผิดข้อ
มันคือการ*ทำให้การแก้ไขปรากฏ* ต่อใครก็ตามที่เก็บ record ก่อนหน้าไว้

ซึ่งเป็นเหตุผลที่ผู้ตรวจสอบจำรากล่าสุดที่เห็นจากคนคนหนึ่ง และเป็นเหตุผลที่
credential ที่ออกไปบันทึกรากที่มันถูกอนุมานมา การย้อน state กลับจึงทิ้ง
credential ที่ถูกเซ็นแล้วชี้ไปยัง state ที่ไม่มีอยู่อีกต่อไป

## ทำให้เล็ก และให้เป็นของคุณจริงๆ

สองอย่างตามมาจากการที่ state ถูกแฮช:

**อย่าเอาค่าที่คำนวณได้ใส่ไว้ในนั้น** ผลรวมที่คุณคำนวณจากสิ่งที่มีอยู่แล้วคือ
สำเนาที่สองของตัวเลข และสำเนาจะไม่ตรงกันในวันที่มีคนแก้อันใดอันหนึ่ง หน้าจอมี
`compute` ไว้เพื่อการนี้พอดี

**อย่าเอา state ของการโต้ตอบใส่ไว้ในนั้น** แท็บไหนเปิดอยู่เป็นของ host ถ้าอยู่ใน
`state` มันจะถูกเซ็นและถูก replay แล้วคำว่า "พิสูจน์ได้" ก็จะมีความหมายน้อยลง
ทีละหนึ่งครั้งที่มีคนกด

ขนาดถูกจำกัดโดย host — totality รับประกันว่าโปรแกรมคุณหยุด และไม่ได้บอกอะไรเลยว่า
ค่าจะใหญ่แค่ไหน `fold` ที่ตัวสะสมโตขึ้นเรื่อยๆ มีจำนวนขั้นจำกัดแต่มีจำนวนไบต์
ไม่จำกัด ขีดจำกัดถูกตรวจก่อน state จะ commit การรันที่จะเกินขีดจึงไม่เปลี่ยนอะไรเลย

## การเปลี่ยนรูปร่างคือเวอร์ชันใหม่

**การเปลี่ยนรูปร่างของ `state` คือเวอร์ชันใหม่ และ state ของมันเริ่มจากว่างเปล่า**
ไม่มี migration ไม่มี compatibility shim ไม่มี dual reader

นั่นเป็นกฎที่เข้มกว่าที่แพลตฟอร์มส่วนใหญ่มี และเหตุผลก็เฉพาะเจาะจง: migration
คือโค้ดที่รันกับข้อมูลที่เวอร์ชันปัจจุบันไม่เคยผลิต ไม่มีใครใช้งานมันจริง และ
**พิสูจน์จาก execution record ไม่ได้เพราะไม่มี action ไหนเป็นคนทำ** ในระบบที่ข้อ
อ้างทั้งหมดคือสิ่งที่รันไปพิสูจน์ได้ ขั้นตอนที่พิสูจน์ไม่ได้ตรงรอยต่อระหว่าง
เวอร์ชันไม่ใช่ข้อยกเว้นเล็กๆ

ผู้ใช้ถูกถามอีกครั้ง และสิ่งที่เขาถูกถามอ่านเข้าใจได้ ก็เพราะไม่มี state ที่สาม
ที่เป็นครึ่งหนึ่งของแต่ละอัน

**ดังนั้นอย่าเอาอะไรที่เสียไปไม่ได้ใส่ไว้ใน `state`** ถ้ามันสำคัญ มันควรอยู่ใน
credential ที่คุณออกให้ — ซึ่งผู้ใช้เก็บไว้ และรอดข้ามเวอร์ชันถัดไปของคุณ —
หรืออยู่บน backend ของคุณเอง
